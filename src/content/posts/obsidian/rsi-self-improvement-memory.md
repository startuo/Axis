## 30 秒答案

递归自我改进（RSI）让**优化器代理**自行改进代理的线束（Harness）：读取失败追踪，编辑提示、工具和完成检查，保留基准测试中得分更高的部分。

但 Google 发现了一个致命问题：**这个方法只在底层模型不变时行得通。** 一套在 Claude Opus 上进化出的线束，移植到 Gemini 后，在 Google 测试的每个领域评分都**低于 Gemini 的普通起始线束**。

原因：线束迁移时，唯一被带走的只有**进化后的代码**（优化器加的提示、检查、规则）。每个部件如何到达那里的记录虽然保留（针对哪种故障、测试时是否修复），但新模型上的优化器**继承了没有理由的更改**——它重试已经失败的实验，或者移除它不理解的修复。

Google 的解法是 **SIM（Self-Improvement Memory，自我提升内存）**——为**优化器本身**保存的日志。每个条目是一个反复出现的问题，以及其下每一次尝试修复的四项记录：**① 编辑及其理由 ② 测试前记录的预测目标 ③ 实际修复了什么（包括失败）④ 测试所用模型与基准**。整个日志每回合录入优化器的提示，新尝试不断追加。

结果：工作区任务有 SIM 84.75 vs 无 SIM 73.42；Coding 领域 10 次运行中 9 次更高，平均 +2.36 分（p=0.003）；4 领域跨数据集+跨模型对比全面碾压「仅传 Harness」「仅传根因」两个基线。

配套的 Comet ML Opik 文章给出了同一闭环的产品形态：**Bad trace → 根因 → diff → 人工批准 → 重跑 → 回归测试锁定**——可观测性只回答「发生了什么」，Opik 把「为什么坏、怎么修、如何不再坏」也自动化了。

## 一、Google RSI 的核心发现

### 1.1 RSI 的机制与 CRSI 的定义

优化器代理的自我改进环路：

```
读取失败追踪 → 编辑提示/工具/完成检查 → 跑基准测试 → 保留得分更高的部分 → 循环
```

**关键区分**：RSI 改的不是模型权重，而是 **Agent 的 Harness（外壳/脚手架）**——提示、工具、完成检查、规则。论文把这一设定命名为 **CRSI（Continual Recursive Self-Improvement，持续递归自我改进）**：让 Harness 优化在**兼容的基准或策略模型之间延续**，而不是每个模型、每个基准都从零开始。SIM 就是为这个"延续"服务的记忆。

### 1.2 跨模型迁移的崩塌

**这是全文最重要的发现**：在 Opus 上进化的线束，迁移到 Gemini 后**全面劣于 Gemini 的原装线束**。

为什么？线束迁移时带走的是**结果，不是过程**：

- 带走的：优化器添加的提示、检查、规则（进化后的代码）
- 留下的：每个部件**为什么存在**——它针对哪种故障、当时修复了什么、为什么这个设计被保留

新模型上的优化器继承了一批「没有理由的更改」，于是出现两种破坏性行为：

1. **重试已经失败的实验**——不知道前人试过且失败了
2. **移除它不理解的修复**——一个为修复特定故障而存在的检查，在新优化器眼里是「多余的复杂」，被删掉，故障复活

> 这是「知识必须携带其理由」的铁律：**只继承结果、不继承理由的进化，会退化成遗忘。**

### 1.3 SIM：优化器自己的记忆

SIM 是为**优化器本身**保存的日志，不是给执行代理用的任务记忆。每个条目是一个反复出现的问题（例如「代理在其命令运行前就声明任务完成」），其下存储每一次修复尝试的完整记录：

| 字段 | 内容 | 为什么需要 |
|------|------|-----------|
| ① 编辑 + 理由 | 改了什么、为什么这么改 | 让后任理解修复的**意图** |
| ② 预测目标 | 测试前记录「要修复的任务是什么」 | 让「预测 vs 实际」可对照 |
| ③ 实际修复 | 真实修复了什么，**包括失败** | 负结果也是知识 |
| ④ 模型与基准 | 测试用的什么模型、什么基准 | 区分「修复有效」与「只在某模型上有效」 |

整个日志每回合录入优化器的提示，随优化进行不断追加。

### 1.4 继承检查的对比案例

论文展示了一个阻止代理「提前声明完成」的检查的继承差异：

- **有 SIM**：优化器读到检查存在的原因，理解后**扩展**它
- **无 SIM**：优化器**重写了同一个检查四次**，其中两次是为了修复**自己制造的死锁**——每一代都在和自己的前代对抗

### 1.5 跨模型接力：Opus 进化，Gemini 继续

这是论文最核心的实验设计：用 **Claude Opus 5.5** 跑完一轮 Harness 进化，然后把 **Harness + 完整 SIM 日志**直接交给 **Gemini 3.8 Flash** 继续优化——**无需从零重跑，新模型不再意味着一切推倒重来。**

### 1.6 实验结果

| 对比 | 结果 |
|------|------|
| 工作区（Workplace）任务 | 有 SIM 最终得分 **84.75**；无 SIM 仅 **73.42** |
| Coding 领域 | 10 次独立源运行中 **9 次**用 SIM 的成绩更高，平均提升 **2.36 分**（p = 0.003） |
| 4 领域、跨数据集 + 跨模型 | 完整 SIM **全面碾压**两个基线：仅传 Harness、仅传根因 |

**核心意义**：进化经验可以**复用、可修订、可累积**。模型换代或任务分布变化时，优化器知道「以前为什么改、改了有没有用」，而不是盲目重试或误删有用组件——这正是 RSI 从「单次实验」走向「持续复利（compounding）」的关键一步。

## 二、Opik：同一个闭环的产品形态

Comet ML 的文章《Your Agent Harness Should Repair Itself》开篇的断语与 Google 的发现互为印证：

> 可观测性工具显示的是代理**做了什么**，以及**几乎没有任何关于如何修复它的信息**。

**当前可观测性平台的分工**：

| 问题 | 谁回答 |
|------|--------|
| 发生了什么 | 平台自动（span 树、延迟、token 成本、仪表盘） |
| 为什么发生 | **你**手动 |
| 怎么修 | **你**手动 |
| 如何不再坏 | **你**手动 |

虚线左边自动、右边靠人——**而生产调试的真正成本全在右边**。模型每次升级带来新的失败模式，工具每次增加带来新的边界情况——线束的复杂化速度快于任何团队手工跟踪修复的速度（Cursor 也分享过围绕代理的线束工程投入之大、且永不结束）。

### Opik 的四层飞轮

```
Trace → Ollie 诊断 → Ollie 提议修复 → 应用并验证 → 测试套件锁定为回归测试 → 回到 Trace
```

| 层 | 机制 |
|----|------|
| **1. Tracing** | `@opik.track` 装饰器一行接入；LangGraph/CrewAI 等 50+ 框架；每次追踪记录活跃的代理配置，保证失败输入可复现重跑 |
| **2. Ollie** | 内建编码代理。无代码访问时读 span 树、识别失败模式、解释跨 LLM 调用的因果链；`opik connect` 后升级为修码模式：读源码 → 定位责任行 → 提出 diff（**不批准不改任何东西**）→ 批准后用原始失败输入重跑 → 并排对比新旧 trace → 把原失败锁定为回归用例 |
| **3. Test Suites** | 用**自然语言断言**替代「标注数据集 + 数值指标」：「响应必须包含具体交易细节，而不只是数量」。每个调试过的失败 trace **自动成为新测试用例**——套件从真实生产失败中生长，而非预先写好的合成场景 |
| **4. Agent Sandbox** | 在 UI 内端到端运行完整代理图；换提示、换模型、加工具，观察整个系统跨完整 span 树的响应；PM、领域专家、QA 无需碰 git 就能安全测试配置 |

**飞轮效应**：每循环一次，线束就更难被打破。人工只出现在一个点：**批准 diff**。

## 三、深度思考：六个问题

**Q1：SIM 的本质是什么？——三层记忆体系**
SIM 是**优化器的元记忆**。它把「进化的理由」变成持久资产。至此可以画出一个完整的三层记忆体系：

| 层 | 记什么 | 实例 |
|----|--------|------|
| 执行层记忆 | 任务的事实与状态 | 代理的 Memory Service（[Claude 记忆架构 - 梦境整理与智能体记忆的组成部分](/posts/obsidian/claude-memory-architecture/)） |
| **优化层记忆（SIM）** | **为什么这个修复存在** | Google 的自我提升内存 |
| 人类层记忆 | 方法论与决策 | Obsidian 知识库 |

SIM 与 [Claude 记忆架构 - 梦境整理与智能体记忆的组成部分](/posts/obsidian/claude-memory-architecture/) 的「梦境整理」在机制上同构：都是**用原始记录（失败 trace）校验和补充记忆（修复的理由）**。区别在于：梦境整理整理的是执行代理的记忆，SIM 整理的是优化器代理的记忆——**进化也需要回查历史**。

**Q2：Opus→Gemini 的崩塌在 Memory Tax 框架里是什么？**
它是 [Memory Tax 论文精读 - 记忆系统的净价值与记忆税](/posts/obsidian/memory-tax-paper/) **鲁棒性维度的完美实证**。论文第三个税源：「固定构建，换 QA 模型，记忆系统的分数波动大于 RAG」——Google 把它推到了极端：换模型后，进化线束**全面劣于原装线束**。税不只是「波动」，是「负净值」。而 SIM 恰好对应论文的补救方向：**保留证据链**。论文说「让偏离可恢复（src-aug）」；SIM 说「让更改携带理由」。两条路指向同一句话：**任何加工过的知识，都必须保留回到原始证据的路径——包括它的「为什么」。**

**Q3：没有 SIM 的优化器为什么重写同一个检查四次？**
这是「进化失忆」：每一代优化器只看当前线束状态（马尔可夫过程），看不到历史决策。结果不是随机游走，而是**系统性的自我对抗**——两次死锁是它自己的修复引入的，然后它又花两次修复自己制造的问题。深一层看：**没有记忆的进化不是进化，是震荡。** 这也解释了为什么很多团队「每换一次模型就重写一次提示词」——他们就是没有 SIM 的优化器。

**Q4：这两篇与你自己的 Skill 自进化指南是什么关系？**
它们是 [Skill 自进化改造指南 - Agent 帮我进化，我只负责反馈](/posts/obsidian/skill-self-evolution-guide/) 的**自动版**。逐项对照：

| 你的指南 | Google SIM | Opik |
|---------|-----------|------|
| 反馈记录 | 每轮追加到优化器提示 | 失败 trace 变回归用例 |
| 「优先从历史反馈和样例中寻找答案」 | SIM 让优化器先读历史 | Ollie 先读 trace 和源码 |
| 「区分单次要求与长期规则」 | ① 编辑理由 + ② 预测 vs ③ 实际 | 回归断言 = 长期规则 |
| 四状态信任阶梯 | 基准测试得分 | 重跑验证 + 回归锁定 |

你的指南是**手工版闭环**（人来当 SIM），Google 和 Opik 是**自动版闭环**（记忆和验证都进系统）。值得注意的差距：你的指南里没有「预测目标 vs 实际修复」的对照字段——SIM 的 ②③ 字段是一个值得偷师的设计：**让优化器在动手前写下它预期修什么，动手后核对**，负结果和正结果一样被记录。

**Q5：Opik 的环路与你知识库里的四个系统是什么关系？**
「Bad trace → 根因 → diff → 批准 → 重跑 → 回归锁定」这个环，与你之前沉淀的四个系统**完全同构**：

- 图工程的评估边：门批评 → 修复者迭代（Opik 的回归测试就是门）
- SuperPlane 的重试环 + 人工升级（Opik 的批准点）
- DeepSeek 的「人只做裁决」（Opik 唯一的 manual step 是批准）
- 十五条的证据制度（「这不是证据」→ 回归断言就是证据的固化）

一个值得注意的深化：[图工程实战 - 如何构建替代循环的代理系统](/posts/obsidian/graph-engineering-practice/) 说过「**门会腐烂**」——六个月前的测试套件可能抓不住今天的失败模式。Opik 给出了反制：**门从真实失败中生长**（每个失败的 trace 自动变成回归测试）。一个只由「预期中的用例」构成的测试套件会腐烂；一个由「真实发生过的失败」构成的套件只会越来越硬。

**Q6：对个人开发者的启示是什么？**
闭环构建的优先级顺序：

1. **先建可观测**（trace）——没有 trace，失败不可复现，一切免谈
2. **再建回归测试**——把每次失败锁成测试用例（这一步纯人工也能做，收益立即）
3. **最后建自动修复**——Ollie/SIM 这类自动修复只有在前两步扎实后才有意义（否则自动修复的就是不可复现的幻觉问题）

这与 [企业级 Agent 架构 - LLM 只是能力组件而非系统](/posts/obsidian/enterprise-agent-architecture/) 的按需架构一致：**先解决「发现与阻止」，再解决「自动修复」**。个人开发者的最小闭环 = trace + 回归测试 + 手工修复——它的自动化程度低，但它闭合。

**Q7：「持续复利」需要哪三个条件？**
CRSI 之所以能从「单次实验」变成「持续 compounding」，缺一不可的三个前提：

1. **优化对象必须是可迁移的层**——改 Harness 而不是改权重。权重跟着模型走，模型一换就归零；Harness 是模型之外的文件，可以整体搬家。这与你知识库里「Agent = Model + Harness」的公式是同一件事的两种说法
2. **记忆必须携带理由**——SIM 的四字段（编辑理由/预测/实际/评估上下文）。没有理由的 Harness 只是「结果集合」，有理由的才是「知识」
3. **评估必须跨模型可比**——否则无法判断迁移后是否仍然有效。论文用跨数据集 + 跨模型 + 配对比较（p=0.003）来保证这一点；这也是「仅传 Harness」「仅传根因」两个基线必须存在的原因：**没有对照，就分不清「迁移成功」和「恰好都变差」**

反过来说，三者缺一，复利立刻变成负债：缺 1 → 经验无法搬家；缺 2 → 新优化器重写同一检查四次（进化失忆）；缺 3 → 你以为在积累，实际在随机游走。

顺带说一句：**你自己的知识库就是这个复利机制的手工版**——每篇沉淀带 `source`（可追溯）、带理由（为什么这么沉淀）、带跨项目连接（可迁移），正是 SIM 四字段的人类形态。区别只在于：Google 把它自动化成了优化器的提示，你把它做成了人的阅读材料。

## 五、一句话带走

> 进化的产物可以迁移，但**进化的理由必须随行**——SIM 保存的从来不是修复本身，而是「为什么这个修复存在」。没有理由的继承，会让每一代优化器都从遗忘开始，甚至与自己对抗。
