## 30 秒答案

问题的起点是一句话：**能不能让 Agent 帮我进化 Skill，我只需要反馈？**

答案是：能，但有前提。Skill 的进化是一个环路——Agent 提议改造 → 用户反馈 → Agent 把反馈转化为结构改进 → 验证。要让这个环**安全地自动转**，需要四个条件：

1. **可验证基底**（卡帕提法则）：只有能被检查的 Skill，才可能被安全地优化。没有验证机制的 Skill，进化就是盲改
2. **反馈分类学**：把每条反馈归类——单次要求还是长期规则；修样例、修检查、还是修工具（优先级：工具 > 检查 > 样例 > 说明文字）
3. **进化预算**：规则不能无限膨胀（记忆税）。每次进化的净价值必须为正——加的是验证与工具，不是散文
4. **信任阶梯**：四种状态（自动验证 / AI 评估 / 人工确认 / 未验证）构成阶梯，进化的方向就是让事项**逐级下移**——从人工判断变成自动检查

人最终只保留三件事：**定一次标准、报错误、判主观。**

本文第一部分是一份**可直接复制的改造指南**（交给有 Skill 文件访问权的 Agent 即可开工），第二部分是深度扩展。

## 一、可复制资产：Skill 自迭代能力改造指南

> 将本指南完整复制给能够访问、编辑你的 Skill 文件的 Agent（如 Claude Code、Codex），并告诉它需要改造的 Skill 路径。Agent 应先阅读现有文件并提供简要诊断，再与用户确认标准，最后实施改造。

### 改造目标

把现有 Skill 从一份依赖 AI 理解和执行的操作说明，逐渐变成一套：

- **结构清晰**：Agent 一眼看懂任务、步骤、依赖、验收条件
- **工具可靠**：重复、确定性的操作有工具支撑
- **结果可验证**：明确要求有自动检查，检查有证据
- **能根据反馈持续改进**：用户报错 → 变成样例/检查/工具修复，不再重复发生

### 第一步：理解现有 Skill

先阅读 Skill 及其关联文件、脚本和参考样例，梳理四件事：

1. **工作地图**：任务目标、执行步骤、输入输出、依赖关系、关键分支
2. **工具能力**：哪些操作已有工具支持？哪些重复、确定性的步骤值得封装成工具？
3. **验证机制**：目前如何判断任务完成、结果正确？哪些要求只有文字说明、没有实际检查？
4. **反馈机制**：用户指出错误后如何修正？能否避免同类问题再次发生？

**尽量保留已有的有效设计，不要为了重构而重构。**

### 第二步：与用户确认验收标准

先根据现有 Skill 提出你理解的标准，再向用户确认。重点问三件事：

1. 好结果是什么样的？哪些要求必须满足，哪些只是偏好？
2. 最不能接受什么错误？过去有哪些反复出现的问题？
3. 哪些环节必须人工确认？哪些可以放心交给 Agent 自动执行？

交互要求：**优先从现有文档、历史反馈和样例中寻找答案；只问缺失或模糊的关键问题，每轮最多 3 个；不要让用户重新解释已有的信息。**

### 第三步：实施改造

1. **结构化**：建立简洁的工作地图，让 Agent 理解任务、步骤、依赖和验收条件
2. **工具化**：把重复、确定性的操作封装成可复用工具。需要时提供统一 CLI 入口，不强制所有 Skill 都开发 CLI
3. **可验证**：把明确要求转化成自动检查，记录检查对象、结果和证据。内容变化后相关验证应重新执行；语义、审美等主观判断保留人工复核
4. **可改进**：建立反馈记录，优先把错误转化为**认可样例、程序检查或工具修复**，必要时再更新 Skill 说明。**区分单次要求与长期规则，避免规则无限膨胀**

### 第四步：测试与交付

- 使用已有样例回归测试，条件允许时再增加真实任务测试
- 对比改造前后结果，确保原有重要功能没有退化
- 未经用户确认，不覆盖重要原始文件或正式交付结果
- 明确区分四类状态：**① 自动验证通过 ② AI 评估通过 ③ 人工确认通过 ④ 尚未验证**

交付时简要说明：改造了什么、为什么；哪些问题现在可以自动检查；哪些仍需要人工判断；以后用户反馈时如何进入下一轮改进。

### 核心原则

- **优先解决真实问题**，不追求复杂架构
- **优先修改工具、检查和好样例，而不是不断增加提示词**
- **没有证据，不宣称验证通过**

## 二、深度思考：五个问题

**Q1：自进化的前提条件是什么？**

是可验证基底。这是卡帕提法则的直接应用：**如果一个任务是可验证的，它就是可优化的**——如果不可验证，它就不可优化。把这句话从任务搬到 Skill 上：**一个 Skill 的进化上限 = 它的可验证程度**。没有自动检查的 Skill，Agent 的每一次改造都是盲改：它无法知道自己改好了还是改坏了，最终退化成「换个说法」。这就是为什么指南把「验证机制」列为理解现有 Skill 的四件事之一、把「可验证」列为改造四维度之一——它不是四个选项之一，是**进化的地基**。

**Q2：反馈如何变成进化？——反馈分类学**

用户说「这里错了」，Agent 收到的不只是一次修正任务，而是一个**分类问题**：

| 反馈类型 | 判定 | 处理 |
|---------|------|------|
| 单次要求 | 「这次用 A 不用 B」 | 只在本次任务应用，**不写入 Skill** |
| 长期规则 | 「以后都要 A」 | 写入 Skill，但优先级最低（说明文字） |
| 可复现的错误模式 | 「同类问题反复出现」 | 转化为**认可样例**（正例）或**检查**（自动拦截） |
| 确定性操作反复出错 | 「这个步骤老做错」 | 封装成**工具**，把判断变成执行 |

**处理优先级：工具 > 检查 > 样例 > 说明文字。** 每一层往右，都更依赖模型的现场理解；每一层往左，都更接近确定性。一条反馈最终停在哪一层，决定了它未来还要再犯几次。这直接呼应 [GPT-6 Astra 技能与提示重审 - 指令减法的艺术](/posts/obsidian/instruction-subtraction/)：提示是提示性的，工具和检查是确定性的——**进化就是把「提示性」的东西逐步迁移到「确定性」层**。

**Q3：进化会失控吗？——进化预算与记忆税**

会。这是 [Memory Tax 论文精读 - 记忆系统的净价值与记忆税](/posts/obsidian/memory-tax-paper/) 的直接推论：**Skill 就是一个记忆系统，每次写一条新规则都是一次 memory construction，都引入税**。规则无限膨胀 = 税无限累积：上下文变长、指令互相矛盾、模型更难判断哪条适用。所以指南里「区分单次要求与长期规则，避免规则无限膨胀」不是洁癖，是**进化预算控制**：

- 每次进化都要问：这条规则**替代**了什么旧规则吗？还是只是**新增**？
- 能变成检查/工具的规则，其税由确定性层吸收（不占模型的判断带宽）
- 只写在文字里的规则，是进化负债——它在消耗模型的注意力，就像 DeepSeek 哲学说的：每条指令都要过「价值 > 注意力成本」的检验

**净价值为正的进化 = 增加了验证或工具，而不是增加了散文。**

**Q4：人到底还需要做什么？——注意力最小集**

你的原问题是「我只需反馈」。这个愿景的完整形态是：人的角色收敛为三个不可外包的动作：

1. **定一次标准**（第二步）：好结果什么样、最不能接受什么错、哪里必须人工确认。这是进化的方向锚点，Agent 无法替你想
2. **报错误**：错误是进化的燃料。人不报错，环路没有能量。报错的方式越具体（给反例），进化越快
3. **判主观**：语义、审美、品味。指南明确把这些保留在人工复核——因为 Agent 无法替你对「好不好」负责

其余一切——诊断、结构化、工具化、写检查、跑回归、写交付说明——都是 Agent 的事。**人的注意力花在「定义」和「裁决」，不花在「执行」。** 这正好是 [DeepSeek 超级代理设计 - 注意力经济学与领域模型](/posts/obsidian/deepseek-superagent-design/) 的注意力经济学在 Skill 进化场景的落地：每轮最多 3 个问题、不让用户重复解释已有信息——把提问也当成预算来管理。

**Q5：四状态信任阶梯意味着什么？**

「自动验证通过 / AI 评估通过 / 人工确认通过 / 尚未验证」不只是交付标签，是一个**信任阶梯**：

```
尚未验证 → AI 评估通过 → 人工确认通过 → 自动验证通过
  （不信任）                                    （完全信任）
```

**进化的本质 = 让事项在阶梯上逐级下移。** 一个新要求第一次出现时是「尚未验证」；Agent 改了、自己评估过是「AI 评估通过」；用户点头是「人工确认通过」；最终它变成了自动检查，从此**永远**「自动验证通过」——用户再也不用为它花注意力。这与 [图工程实战 - 如何构建替代循环的代理系统](/posts/obsidian/graph-engineering-practice/) 的门等级（硬门 > 软门 > 人类门）完全同构：**门越硬，人的注意力越省，但迁移需要证据积累。** 没有证据，不宣称验证通过——因为声称跳级（把「AI 评估」说成「自动验证」）就是在偷走你自己的注意力预算。

## 四、下一步：从「改造指南」到「常驻进化者」

你的愿景（agent 帮我进化，我只需反馈）的最终形态可以再推一步：把这份**一次性改造指南**升级为**常驻进化机制**——结合 [DeepSeek 超级代理设计 - 注意力经济学与领域模型](/posts/obsidian/deepseek-superagent-design/) 的触发器思路：

```
触发（Skill 执行失败 / 用户报错 / 周期检查）
  → Eval（是否值得进化？单次问题还是长期规则？）
  → 改造（工具 > 检查 > 样例 > 说明，四层修复）
  → 门（回归测试 + 证据记录）
  → 人的裁决（只出现在主观判断点）
```

这时 Skill 就不再是「文件」，而是一个有生命周期的系统：**结构承载执行，工具承载确定性，检查承载信任，反馈承载进化**——人只做定义与裁决。这个方向值得在现有 Skill 上试点：挑一个高频使用的 Skill，跑一次完整改造，看进化环路是否真的转起来。
