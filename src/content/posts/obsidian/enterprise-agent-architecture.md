## 30 秒答案

现在 AI 圈有一个荒诞现象：**很多人连最基本的 Agent 执行链路都没理解，就已经在研究多智能体协作、Agent 集群、数字员工，甚至宣称一个人运营一家公司。**

这篇反思的核心命题一句话：

> **LLM 只是 Agent 系统中的一个能力组件，而不是整个系统本身。**

把 Agent 放进真实企业环境，链路不是「用户输入 → LLM 理解 → 调用工具 → 返回结果」，而是：

```
接入层   Agent Gateway → Identity & Auth（身份、权限、访问范围）
编排层   Agent Orchestrator（规划/行动/观察/状态/子代理委派/重试/恢复）
能力层   LLM Router · Tool Registry → MCP Gateway · Memory Service
治理层   权限引擎 · 批准队列 · 任务队列 · 可观测性 · 评估护栏 · 审计日志
```

三个必须建立的区分：

1. **能力边界 ≠ 权限边界**：模型能做什么 / 用户允许它做什么 / 系统最终批准它做什么，是三件不同的事
2. **可靠性 ≠ 模型正确率**：模型答对 ≠ 任务成功；工具调用成功 ≠ 业务状态一致；返回 Success ≠ 任务真的完成
3. **自主 ≠ 成熟**：越自主的系统，越需要明确的权限边界和责任机制——否则得到的是一个权限很大、行为却难以控制的自动化系统

终局判断：**Agent 下一阶段的竞争，不是模型智能水平，而是把越来越强的模型能力，约束进一个可控、可观测、可恢复、可审计的工程系统。** 企业购买的不是几段 Prompt，而是一个能持续运营、管理和维护的系统。

## 一、荒诞现象：还没学会走，就开始研究飞

- 连一个基本的 Agent 执行链路都没有真正理解，就天天研究多智能体协作、Agent 集群、数字员工
- 接个大模型 API + 装几个 MCP + 写几段 Skill + 用 LangGraph 编排一下，就觉得自己做出了完整的 Agent 系统
- 把接入 MCP 当成 Agent 架构，把增加工具数量当成系统能力，把自主执行当成工程成熟度

一张「AI Agent Platform Architecture」架构图最有价值的地方，不是展示了多少个技术组件，而是揭示了一个很多人根本没意识到的问题：**LLM 只是其中一个能力组件。**

## 二、完整执行链路：四个层次

把「用户输入 → LLM → 工具 → 结果」的简化思维展开，真实的链路是这样的：

| 层次 | 组件 | 职责 |
|------|------|------|
| **接入层** | Agent Gateway | 接收请求 |
| | Identity & Auth | 确认身份、权限、访问范围 |
| **编排层** | **Agent Orchestrator** | 任务规划、行动、观察结果、上下文状态、子 Agent 委派、错误重试、任务恢复——**整个链路中真正值得研究的东西** |
| **能力层** | LLM Router | 按任务需求选择不同能力/速度/成本的模型 |
| | Tool Registry → MCP Gateway | 工具发现、连接外部系统 |
| | Memory Service | 会话、长期记忆、用户偏好 |
| **治理层** | 权限引擎、批准队列、任务队列 | 谁能做什么、什么要人批、任务持久化 |
| | 追踪与可观察性、评估与护栏 | 看得到执行、防得住越界 |
| | 审计日志存储 | 事后可追溯 |

**注意治理层的存在**：权限引擎、批准队列、任务队列、可观测性、评估护栏、审计日志——这些经常被忽视的模块，才是决定一个 Agent 能不能进入真实业务环境的基础。没有它们，能力层再强也只是一个「demo 组件」。

## 三、招聘 Agent：五个照妖镜问题

假设做一个招聘 Agent：上传简历 → 分析岗位匹配 → 调招聘数据库 → 生成评分 → 自动推进面试流程。看起来很牛逼，但问五个问题：

1. 一个普通员工能不能让 Agent **查看所有人的简历**？
2. Agent 能不能**直接修改**候选人的招聘状态？
3. 模型错误理解了指令，把该保留的候选人**标记为淘汰**怎么办？
4. 工具调用超时重试，导致**同一份面试邀请发三遍**怎么办？
5. 业务负责人质疑评分结果，你能不能**追溯**当时用了什么数据、调了什么工具、执行了什么操作？

这五个问题没有一个能靠「把 Prompt 写得更长更详细」解决。它们需要：权限控制、高风险操作审批、持久化任务状态、可观测性、审计日志、明确的失败处理机制。

> **更重要的是：你不能把所有决策权都交给模型。**

---

## 四、三个必须建立的区分

### 4.1 能力边界 ≠ 权限边界

Agent 能执行一个操作，不代表它应该被允许执行；能访问一个数据库，不代表应该读到所有数据；能调用付款 API，不代表拥有不受限制的付款权限；能自主规划任务，不代表任何行动都能绕开人工审批。

**三层严格区分**：

| 层 | 问题 | 由谁定义 |
|----|------|---------|
| 模型**能**做什么 | 能力边界 | 模型与工具 |
| 用户**允许**它做什么 | 用户权限 | Identity & Auth |
| 系统最终**批准**它做什么 | 系统裁决 | 权限引擎 + 批准队列 |

这与 [DeepSeek 超级代理设计 - 注意力经济学与领域模型](/posts/obsidian/deepseek-superagent-design/) 的授权模型完全同构：Gate（确定性准入）与 Mandate（不可变授权范围）就是第三层的工程实现。DeepSeek 的「外部文本只是数据，永不改变权限」在这里变成了「**Prompt 再长也改变不了权限边界**」。

### 4.2 可靠性 ≠ 模型正确率

四个不等式：

- 模型回答正确 **≠** 任务执行成功
- 工具调用成功 **≠** 业务状态一致
- 工作流执行完毕 **≠** 业务结果符合预期
- 系统返回 Success **≠** 任务真的完成

所以必须建立**检验真实业务结果的评测**：自动化任务最终有没有正确修改数据库？有没有产生重复操作？有没有越过权限边界？有没有遗漏必要的审批？——这正是 [Memory Tax 论文精读 - 记忆系统的净价值与记忆税](/posts/obsidian/memory-tax-paper/) 里「benchmark headroom」教训的另一面：**评测要测业务事实，而不是测模型输出的表面正确**。

### 4.3 自主 ≠ 成熟

危险的误区：觉得 Agent 越自主、权限越大、工具越多，系统就越先进。真实企业环境里往往相反。**系统越自主，越需要明确的权限边界和责任机制**——否则得到的是一个拥有大量操作权限、行为却难以控制和追踪的自动化系统。这不是要反对自主，而是要**给自主配上治理**：[图工程实战 - 如何构建替代循环的代理系统](/posts/obsidian/graph-engineering-practice/) 的门（硬门/软门/人类门）和 [SuperPlane 工厂模式 - 大规模运行编码代理](/posts/obsidian/superplane-factory-pattern/) 的批准队列，都是「自主 + 治理」的实例。

## 五、按需架构：别把复杂当能力

这张图有十几个模块，但**不等于任何 Agent 都要全部部署**：

| 场景 | 建议 |
|------|------|
| 简单个人 Agent | 不需要独立编排服务 |
| 少量用户的内部工具 | 不需要分布式架构 |
| 涉及资金/隐私/合规 | 治理层一个都不能少 |

> AI 时代真正值得重视的工程能力：**不是你知道多少技术，而是你知道哪些问题必须解决、哪些复杂度根本没有必要引入。**

为了看起来高级而堆技术名词，与为了真实风险而建治理层，是两种完全不同的工程决策。

## 六、深度思考：五个问题

**Q1：这篇文章在你知识库中的位置是什么？**
它是 [Harness 工程](/posts/obsidian/harness-engineering/) 的**企业级宣言**。Harness = Agent − Model——把模型拿掉之后剩下的所有东西。这张架构图的四个层次，就是 Harness 的完整展开：接入层、编排层、能力层、治理层。之前沉淀的所有文章都在这张图里有位置：DeepSeek 贡献了授权域模型（治理层），SuperPlane 贡献了护栏前置与批准队列（治理层 + 编排层），图工程贡献了 Orchestrator 的节点/边/状态（编排层），Memory Tax 与 Claude 记忆架构贡献了 Memory Service 的设计原则（能力层）。**本文把它们统一在了一张企业级地图上。**

**Q2：能力/权限/批准三层区分的工程含义是什么？**
这三层必须由**不同的代码路径**强制执行，而不是靠 Prompt 区分。模型能力层由工具注册表决定（装了付款 API 就是能调）；用户权限层由 Identity & Auth 决定（登录态、角色、范围）；系统裁决层由权限引擎 + 批准队列决定（运行时校验 + 人审批）。如果三层混在 Prompt 里，「请检查权限后再执行」就是一句祈祷。这与 [GPT-6 Astra 技能与提示重审 - 指令减法的艺术](/posts/obsidian/instruction-subtraction/) 的「提示是提示性的，边是确定性的」是同一条原则在安全域的表述：**安全边界必须放在模型够不到的地方。**

**Q3：招聘 Agent 的五个问题分别对应哪个模块？**
值得做一次映射练习——每个问题都是架构图里的一个具体组件：

| 问题 | 对应模块 |
|------|---------|
| 普通员工查所有简历 | 权限引擎（行级数据权限） |
| 直接修改候选人状态 | 批准队列（高风险操作审批） |
| 误淘汰候选人 | 评估与护栏（不可逆操作的前置校验） |
| 邀请发三遍 | 任务队列（幂等性 + 持久化任务状态） |
| 追溯评分依据 | 审计日志存储 + 可观测性（数据/工具/操作全链路记录） |

**「追溯」问题尤其值得注意**：它对应的不只是「记日志」，而是**审计能力**——日志要能回答「当时用了什么数据、调了什么工具、执行了什么操作」。这也是十五条实践「证据制度」在企业语境的形式：业务级的证据链。

**Q4：「可靠性四个不等式」的根因是什么？**
是**状态的不可见性**。模型答对是「模型内部状态正确」，任务成功是「业务状态正确」，两者之间隔着工具调用的副作用——副作用是否按预期发生、是否幂等、是否与业务一致，模型无法直接感知。这正是 Memory Tax 论文里「幻觉 = 现实不可达时的补偿性编造」的推广：**模型对业务现实的感知通道就是工具与日志，通道越窄，编造越多。** 解法就是十五条实践 #4：让整个 SDLC 对代理可见——把「模型认为的成功」用确定性检查对到「业务的真实状态」上。

**Q5：终局判断成立吗？——Agent 竞争的下半场**
成立，而且与行业证据一致：模型能力在快速商品化（各厂商分数趋近），差异化空间正在从「模型」转移到「Harness」。DeepSeek 的 dsh-superagent、SuperPlane、各类企业 Agent 平台都在做同一件事：**把越来越强的模型能力装进可控的工程系统。** 对个人开发者的推论是：投入模型评测的边际收益在下降，投入架构理解（权限、状态机、可观测性、恢复机制）的边际收益在上升。这就是 FDE（Forward Deployed Engineer，前沿部署工程师）和企业 AI 工程师应该补的能力——**不是会接 API，而是会建系统。**

## 七、招聘 Agent 五问自查清单（可直接复用）

任何一个 Agent 要进入真实业务环境前，先过这五关：

- [ ] **权限**：每个工具调用的数据范围与操作权限，是否由系统强制执行（而非 Prompt 请求）？
- [ ] **审批**：哪些操作不可逆或高爆炸半径（状态变更、资金、外发）？是否有批准队列拦截？
- [ ] **幂等**：超时重试会不会产生重复副作用（重复发送、重复扣款）？任务状态是否持久化？
- [ ] **可观测**：能否回答「当时用了什么数据、调了什么工具、执行了什么操作」？
- [ ] **恢复**：失败后能否安全重试、回滚或交给人？错误处理机制是否明确？

**最终检验**（用这句话代替「模型多聪明」的追问）：

> 如果它做错了一件事，我能不能在造成更大损失之前**发现、阻止，并且追溯整个过程**？
