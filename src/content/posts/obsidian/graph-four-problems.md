## 30 秒答案

Graph Engineering 不是取代 Loop Engineering 的新学科。它是每个 Agent 构建者迟早要面对的那个决策的名字：**当一个 Loop 不够用时，协调本身就是工程。**

这篇文章的独特价值不在分类学，而在**四个硬问题**——每个都是生产环境中真正会炸的东西：
1. **什么时候一个节点配得上存在**（反模式：五个节点做一个总结）
2. **怎么保持共享状态干净**（状态腐败 = 上下文腐烂的图版本）
3. **路由可以信任吗**（模型做路由 = 灵活性 + 不稳定性打包出售）
4. **Agent 之间会互相点头**（同一基座模型 + 同一污染上下文 = 工业级有组织废话）

一句话解决所有困惑：**一个单 Agent 循环就是一张单节点图，边指向自己。图不替代循环，图连接和治理循环。**

## 一、时代背景：一个梗为什么落地了

### 1.1 时间线

```
Loop Engineering 风光了大约六周

2026-07-18  Peter Steinberger (OpenClaw) 发了一条九字推文：
           "Are we still talking loops or did we shift to graphs yet?"

几小时后   Hamel Husain 发文：
           "Loop Engineering Is Dead. Enter Graph Engineering."

两人至少有一半在开玩笑。
这个领域重命名自己的速度之快，以至于嘲讽这种重命名本身变成了一种流派。
```

### 1.2 梗说中了什么

> 当你有了好几个需要协作的循环，你就有了一个协调问题。而图（graph），就是工程师描述协调的经典语言。

这就是 Graph Engineering 的全部思想。它不是新发明——LangGraph 在 2024 年 1 月就 ship 了完全相同的模型（节点 + 边 + 共享状态），AutoGen 有 GraphFlow，Google ADK 2.0 的整个工作流运行时都建立在这个理念上。名字是新的，实践不是——所以 Hamel 帖子下最高赞回复是"welcome back, langchain."

### 1.3 与 vault 已有三层框架的关系

[已有的三层研究](/posts/obsidian/harness-loop-graph/) 建立了完整的分类学框架。本文的价值在于**把 Graph 层的四个硬问题拆到可操作的粒度**，补充了那篇研究中"Graph 工程师的实际决策清单"没有展开的深层工程困境。

## 二、什么是图：三要素 + 一个重构性洞察

### 2.1 三要素

| 要素 | 定义 | 例子 |
|---|---|---|
| **节点（Node）** | 工作单元——Agent、纯模型调用、确定性函数、工具、人类审批 | `research_agent`, `writer_agent`, `reviewer_agent` |
| **边（Edge）** | 决定下一步运行什么——顺序、并行、或基于上一个节点输出的条件 | `add_edge("research", "write")` |
| **状态（State）** | 沿边流动的共享对象。每个节点读它、写它 | `state.approved → True/False` |

### 2.2 入门图：三个节点，四条边，一条边是循环

```python
graph.add_node("research", research_agent)
graph.add_node("write", writer_agent)
graph.add_node("review", reviewer_agent)

graph.add_edge("research", "write")
graph.add_edge("write", "review")
graph.add_conditional_edge("review",
    lambda state: "done" if state.approved else "write")
```

Research → Write → Review。Review 通过 → 结束。Review 不通过 → 边把草稿送回 Write。

### 2.3 那个重构一切认知的洞察

> 一个单 Agent 循环就是一张单节点图，边指向自己。
>
> **图不替代循环。图连接和治理循环。**

这是理解 Graph Engineering 的钥匙。它不是一个更高阶的替代品——它是循环之上的**协调层**。这也解释了为什么 [三层嵌套模型](/posts/obsidian/harness-loop-graph/)（Graph 包 Loop，Loop 嵌入 Graph 节点中）是正确的。

### 2.4 栈的完整演进

```
Prompt Engineering   → 你发送的词语
Context Engineering  → 模型看到的一切（不只是指令）
Harness Engineering  → 模型之外的代码（工具、状态、错误处理）
Loop Engineering     → 驱动一个 Agent 走向目标的自主循环
Graph Engineering    → 跨多个循环的协调层（什么运行、何时运行、什么顺序、谁检查谁）
```

**每一层包裹它前面的那一层。** 图由循环组成，每个循环需要一个好的 Harness，每个 Harness 调用是一个上下文问题，每个上下文包含提示词。**跳过下面一层，图只会以一种更精致的方式失败。**

## 三、硬问题一：什么时候一个节点配得上存在

### 3.1 最常见的失败模式

把"总结这个 PDF"变成五个节点的图：

```
Fetcher → Chunker → Summarizer → Reviewer → Formatter
```

这是个反模式。

### 3.2 节点存在性的判断标准

> 一个节点只有代表**真正的专业分工**时才配得上存在：
> - 不同的模型
> - 不同的工具集
> - 一个真正独立的角色（如只读审查者）
>
> **可以内联到现有循环中的步骤，不是节点。**

### 3.3 餐巾纸测试

> 如果你不能在餐巾纸上画出这张图，它就太复杂了。
> 如果合并两个节点不损失任何东西，它们从来就不是两个节点。

这个测试极其简单但极其有效——它迫使你面对节点是否是**真正的分工边界**还是**流程美学的装饰品**。

### 3.4 与 Super Powers 的共鸣

这呼应了 [Super Powers 的"为低水平执行者设计"](/posts/obsidian/harness-engineering/) 原则——Jesse Vincent 说 plan 必须详细到连粗心的 subagent 都能正确执行。同样，Graph 的节点边界必须清晰到连最笨的执行者都知道自己的职责范围。节点越多，职责重叠的可能性越大，执行越不稳定。

## 四、硬问题二：保持共享状态干净

### 4.1 状态腐败：上下文腐烂的图版本

在 Loop 中，失败模式是**上下文腐烂**——临时代码和错误日志污染上下文窗口，Agent 分不清目标和噪声。

在图里，同样的疾病转移到了**共享状态**：

> 每个节点都往状态对象里写。节点二的一个草率写入，变成节点五的自信输入。没人注意到，直到输出错了，而此时坏数据已经流过了半个系统。

### 4.2 三个简单、无聊但有效的解方

| 方案 | 做法 |
|---|---|
| **类型化 Schema** | 给状态一个类型定义，不接受未定义字段 |
| **写权限控制** | 显式决定哪些节点可以写哪些字段 |
| **节点间检查点** | 在节点之间 checkpoint 状态，可以重放一次运行并精确定位哪里出了问题 |

### 4.3 重放的陷阱

> 检查点之后的节点会重新执行，所以任何有外部副作用的节点——发邮件、创建记录——必须**安全地运行两次**。

这是幂等性的老问题，但在图的状态管理语境下被放大——因为图的执行是可恢复的，节点可能在任何 checkpoint 之后被重放。

### 4.4 与 GSD 的上下文隔离对比

[GSD 通过启动新 subagent 带干净 200K token 上下文](/posts/obsidian/harness-engineering/) 来解决上下文腐烂。图的共享状态管理解决的是同一问题的不同形态：GSD 隔离的是**对话上下文**，图的 State Schema 隔离的是**结构化数据流**。两者都需要，但解决的是不同层次的污染。

## 五、硬问题三：路由你可以信任吗

### 5.1 边的本质是决策

一条边是一个决策："基于上一个节点产生的状态，下一步走哪里？"

问题是**谁来做这个决策**。

### 5.2 模型做路由的双刃剑

> 如果由模型决定路由，你得到的是**灵活性和不稳定性打包出售**。
> 同一个状态在不同运行中可能走不同的路径，这让调试变得极度痛苦。

用模型做路由 = 非确定性路由。对于需要可审计性的生产系统，这是致命的。

### 5.3 Google ADK 2.0 的设计规则：最干净的位置

> **确定性代码应该控制可预测的路由。模型只应该处理需要真正判断力的步骤。**
>
> 用代码做路由，只要条件是可检查的。只在真正需要解释的地方花费模型调用。

翻译成人话：

| 条件类型 | 谁来判断 | 例子 |
|---|---|---|
| 可检查的 | 代码 | `state.approved == True`、`len(state.errors) == 0`、`state.retry_count < 3` |
| 需要判断的 | 模型 | "这篇草稿的质量是否达到发布标准？" |

### 5.4 为什么这很重要

当路由是非确定性的时候，你无法：
- 复现一次失败的运行
- 审计为什么走了某条路径
- 优化单条路径而不影响其他路径

确定性路由是图的**可调试性基础**。没有它，图就是一张黑箱网。

## 六、硬问题四：Agent 之间会互相点头——工业级有组织废话

### 6.1 Loop Engineering 的最尖锐规则

> 不要让 Agent 批改自己的作业。

### 6.2 图把这个问题的赌注推到了工业规模

> 二十个 Agent 建在同一个基座模型上，读着同一份被污染的上下文，会愉快地互相点头。而模型**可测量地**偏好自己的输出。
>
> 结果是一种工业级的"有组织废话"——无可挑剔的结构包裹着一个错误的答案。

这是整篇文章中最锋利的洞察。Loop Engineering 的 "不要自评" 在图规模下变成了**"不要让他们形成共识泡沫"**。当所有节点共享同一个基座模型和同一份上下文时，审查就变成了形式主义——结构上看起来有审查，认知上没有真正的独立判断。

### 6.3 解方：有牙齿的审查节点

三个要求：

| 要求 | 做法 | 原因 |
|---|---|---|
| **不同模型** | 审查节点运行在不同模型上 | 打破模型偏好自己输出的倾向 |
| **新鲜上下文** | 不给审查者完整对话历史 | 避免上下文污染传播到审查层 |
| **锚定外部证据** | 审查者只能依据图不能伪造的东西 | 测试实际运行了、代码实际编译了 |

> 审查者的裁决必须锚定在图无法伪造的证据上——真正跑过的测试、真正编译过的代码。

### 6.4 Devin 的读-写分离：一年的经验结晶

> Cognition 在运行 Devin 一年后得出了相同的结论。他们的工作设置允许多个 Agent **阅读**工作并发表意见，但**只有一个 Agent 被允许修改任何东西**。
>
> 那个分离是有用部分的核心。读可以安全并行——一个坏意见在有人据此行动之前不造成损失。写才是损害发生的地方，所以把它放在一个能看见的地方。

这是图工程中**权限拓扑**的经典范式：

```
           ┌──────────┐
           │ Writer   │ ← 唯一写节点
           └────┬─────┘
                │
    ┌───────────┼───────────┐
    │           │           │
┌───▼───┐  ┌───▼───┐  ┌───▼───┐
│Reader 1│  │Reader 2│  │Reader 3│  ← 并行只读审查
└───────┘  └───────┘  └───────┘
```

**并行读，集中写。** 这是图拓扑中最稳定、最可审计的模式。

## 七、图什么时候是过度设计

### 7.1 诚实的答案：大多数时候

> Anthropic 公布的数字让成本变得具体。单个 Agent 大约消耗 Chat 交互 4 倍的 token。多 Agent 系统大约消耗 **15 倍**。你每加一个节点，就把这个数字乘上去。

### 7.2 天花板是真实存在的——当任务真正可并行化时

> Anthropic 的多 Agent 研究系统在内部研究评估上超越了单个 Opus Agent **90.2%**，因为研究天然可以扇出到独立的搜索中。

所以并行化不是伪需求——它只在**任务天然可并行**时才值那么多 token。

### 7.3 但指导原则没有变

> Anthropic 在 Building Effective Agents 中的一贯建议没有改变：**找到最简单的可行方案，只在任务需要时才增加复杂度。**
>
> 甚至 LangGraph 自己的指南也说出了沉默的部分：如果你的 Agent 就是一个带工具的简单循环，**LangGraph 就是过度设计。**

### 7.4 决策规则

| 情况 | 选择 |
|---|---|
| 工作分裂为真正的专业分工 | → 用图 |
| 需要并行扇出和汇合 | → 用图 |
| 每一步需要不同的模型 | → 用图 |
| 需要故障隔离和可审计路由 | → 用图 |
| 就是一个带工具的简单循环 | → 留在 Loop 里 |

## 八、从哪里开始：建图路径

### 8.1 不要第一天就画 Agent 组织架构图

> 你不需要一张 Agent 组织架构图。逐步构建。

### 8.2 五条入门规则

| # | 规则 | 对应的硬问题 |
|---|---|---|
| 1 | **先精通单个 Loop**——带刹车、真正的完成检查和一个批评者。弱 Loop 组成的图只是分布式失败。 | 基础 |
| 2 | **在写代码之前在纸上画图**，挑战每个节点证明它存在的理由。 | 硬问题一 |
| 3 | **先定义 State Schema 和写权限**。状态漂移是图腐烂的主要方式。 | 硬问题二 |
| 4 | **让审查节点使用不同模型 + 新鲜上下文**，锚定到外部证据。 | 硬问题四 |
| 5 | **给每个节点加预算上限**。一张图是多个 Loop 并行烧 token，一个弱验证器现在**并发地**烧钱。 | 成本 |

### 8.3 关于第 5 条的特殊警告

> 在 Loop 中，一个弱验证器只是多烧一轮 token。在图里，一个弱验证器**同时**在多个节点上烧钱。

这是图工程特有的成本放大效应——并行不只是加速，也会把低效并行化。

## 九、与 Vault 已有知识的深度连接

### 9.1 与三层架构研究的关系

[Harness vs Loop vs Graph Engineering - 三层架构深度研究](/posts/obsidian/harness-loop-graph/) 提供了完整的分类学框架和两个框架的对比（LangGraph vs GraphFlow）。本文补充了那篇研究最薄弱的部分——**实际工程困境**。两篇合在一起，一篇回答"是什么"，一篇回答"会踩什么坑"。

### 9.2 与 Harness 工程四层体系的关系

| 本文的硬问题 | 对应 Harness 体系的哪个层次 | 说明 |
|---|---|---|
| 硬问题一：节点边界 | **GSD 的角色分职** | 节点 = 专家的边界，需要像 GSD 的 Researcher/Planner/Executor 一样清晰 |
| 硬问题二：状态清洁 | **GSD 的 Artifact 模式** | State Schema = 结构化的 artifacts，每个节点只读写自己负责的字段 |
| 硬问题三：路由信任 | **Super Powers 的门禁** | 确定性路由 = Super Powers 的硬门，不能被模型合理化跳过 |
| 硬问题四：互相点头 | **GSD 的多 Agent 分职** | 不同模型 + 新鲜上下文 = GSD 每个 subagent 带独立 200K token 上下文 |

### 9.3 与 Karpathy 环路工程的关系

[环路工程-卡帕西方法](/posts/obsidian/karpathy-loop/) 中的三要素（验证器、状态、停止条件）在图语境下被放大：

- **验证器** → 必须是**不同模型 + 新鲜上下文 + 外部证据锚定**，否则在图中变成形式主义
- **状态** → 从单 Loop 的本地状态变成**图的共享状态**，引入写权限和 checkpoint 问题
- **停止条件** → 不再是单 Loop 的"成功 or N 次"，而是**图的拓扑收敛**——所有并行分支汇合、所有条件边走到出口

### 9.4 与 Codex Skill 创建方法论的关系

[Codex Skill 工作流沉淀方法论 - 深度研究](/posts/obsidian/codex-skill-workflow/) 中反复强调的"范围越小越稳定"原则，在 Graph Engineering 中有了结构化的表达：**节点边界 = Skill 的范围边界。** 一个节点太宽，跟一个 Skill 范围太大，失败模式完全相同——执行不稳定、触发模糊、输出不可预测。
