## 30 秒答案

两篇互为上下篇的材料：**Anthropic 官方首次给出 Harness 的六层结构**（工具/上下文/权限/钩子/验证/评估），并附一个 20 行提示词——粘贴给 Claude Code 就能让它帮你为现有代理设计线束；随后是环路与图的进阶课程，补上了此前图工程实战里没讲透的**五条进阶法则**。

> **两个跑同一模型的代理，差异可以大于两个不同模型的差异。差异就是 Harness。** 提示工程 → 上下文工程 → 线束工程——模型是发动机，Harness 是整辆车。

官方六层一句话版：**工具少而专、错误会教人**；**上下文短、按需加载、满了压缩**；**读测自动、危险问人、一切沙盒**；**钩子无例外**；**新审阅者读 diff 不读摘要**；**每次改动都评分、保留赢的**。

课程五条进阶法则：**先写可失败的检查**（没有检查的循环只是调度器）、**边=数据依赖**（说不出跨越的变量名就没有边）、**环在节点内、图在节点间**、**两条返回路径**（纠错边修这一次，学习边修以后每一次）、**按爆炸半径开车道而不是按置信度设阈值**（置信度是唯一能被模型影响的变量）。

## 一、Anthropic 官方：Harness 六层

摘要原文的洞察：**同一个模型上的两个代理，差异可以比两个模型之间的差异更大。** 差异来自 harness——代理能调用什么工具、什么进入上下文、被允许做什么、每步前后自动触发什么、工作如何被检查、变更如何被度量。

| 层 | 官方做法 | 关键细节 |
|----|---------|---------|
| **1. Tools** | 工具要少，一个工具一份工作；合并重叠 | **每条错误消息都告诉代理下一步该试什么**（图 1a："not found: try search"）——错误是教学，不是抱怨 |
| **2. Context** | CLAUDE.md 保持短：目标、约定、命令；文件按需加载 | 长会话压缩时**保留决策、丢弃原始输出** |
| **3. Permissions** | 读+测试 → 自动；编辑 → 沙盒；部署+删除 → 问人 | 一切都在沙盒里跑 |
| **4. Hooks** | 工具运行前：拦截 secrets/lockfiles/受保护路径的编辑；每次编辑后：format/lint/typecheck | **每次都触发，没有例外**（fire every time, no exceptions） |
| **5. Verification** | 一个**新鲜上下文**的审阅者读 **diff 而不是摘要**，跑测试 | 检查通过前什么都不算完成；失败→修复→重跑 |
| **6. Evals** | 每次 harness 变更都在评估集上评分：成功率、tokens、轮数 | 保留得分更好的；**记录每次运行使失败可重放**（图 1f：v1 58% → v4 91%） |

### 官方 20 行提示词（完整可复制）

> 花括号字段由用户填写，其余原样使用。在 Claude Code 中以 Fable 5.2 运行。

```
HARNESS ENGINEER - FABLE 5.2
{AGENT} · {REPO} · {RISKY ACTIONS} · {EVAL SET}
01 TOOLS
Audit every tool. Merge overlaps; each does one job with a plain description.
Every error message says what went wrong and what to try next.
02 CONTEXT
Keep CLAUDE.md short: goals, conventions, commands. Load files on demand.
Compact long sessions: keep decisions, drop raw output.
03 PERMISSIONS
Reads, tests and safe retries run without approval.
{RISKY ACTIONS} always ask first. Everything runs in a sandbox.
04 HOOKS
Before tool use: block edits to secrets, lockfiles and protected paths.
After every edit: format, lint and typecheck automatically.
05 VERIFICATION
A fresh reviewer reads the diff, not the summary, and runs the tests.
Nothing is done until the check passes. Fail, fix, rerun.
06 EVALS
Score every harness change on {EVAL SET}: success rate, tokens, turns.
Keep what scores better. Log every run so failures can be replayed.
```

**6 层。1 个提示。0 个无限循环。**

## 二、环路的本质：一个可以失败的检查

剥掉一切，环只有四个部分：**produce → check → correct → repeat until green**。

> **检查才是全部。** 没有一个「你不在场时也能让工作失败」的东西，你拥有的不是环，是调度器。

几乎没人先写检查。人们先建工作，再在末尾栓上一个「审查」——而那个审查是另一个模型看输出。**两个乐观主义者互相点头。**

先写条件，写成程序可判定的形式：

```
GREEN      测试套件退出码为 0
GREEN      每条断言都带来源行
GREEN      diff 只触碰计划中列出的文件
NOT A CHECK   输出看起来不错
NOT A CHECK   模型说它有信心
NOT A CHECK   没有抛出错误
```

最后一条专门坑细心的人：**没有错误 ≠ 正确的证据。** 建立在这上面的环，会自信地重复同一个错误直到预算烧光，全程日志干净。

### 环的天花板

环让**一个工作单元**变好——这是它的全部工作，它非常擅长。但它不能决定哪些单元存在、什么顺序、也注意不到五个步骤里有两个根本不需要互相等待。于是你得到一个非常好的代理，**跑着错误的三个步骤、错误的顺序、一次一个**。每步都对，结果仍然慢且形状错误——调环救不了，因为故障不在任何单元内部。**这就是人们开始怪模型的时刻，也是上一层开始回本的时刻。**

## 三、图的五条进阶法则

### 3.1 边 = 数据依赖，「然后」不是边

图只有两样东西：节点（一份有界工作：一进一出）、边（这个节点的输出喂那个节点的输入）。

> **每一个不必要的等待背后，都是把「and then」当成了边。**

「总结这个文件，然后查天气」——天气不消费摘要，两者之间没有边。它们是被线性脚本串起来的两个独立节点，串联来自你打字的顺序。

**可执行的测试**：对你现有管线的每一条箭头问——下一步真的读上一步的输出吗？**说不出跨越箭头的那个变量名，就没有边，等待纯属浪费。** 大多数链条里有两三条这样的假边，找出来通常是最大的单项提速。

### 3.2 四种节点，其中一种不是模型

**Splitter、worker、code node、gate——这就是全部词汇表。**

| 节点 | 职责 | 关键 |
|------|------|------|
| **Splitter** | 把工作切成单元，坐在最前面 | **它决定得最多**：按错误维度切分浪费下游一切。按文件夹切仓库 → 四个 worker 审同三个文件；按爆炸半径切 → 每个看到别人看不到的 |
| **Worker** | 一个单元、一个视角、**自己的上下文** | 给四个审计员共享窗口，他们会收敛：第一个写了发现，其余读到，四份报告围着同一件事——**你付了四倍的钱买一个观点加三个回声** |
| **Code node** | 合并、排序、去重、前后对比 | **人们忘了它存在**。判据：如果描述这个转换不用「判断/决定/评估/总结」这些词，它就是代码。每个只有一个正确答案的转换过模型 = 给零方差的步骤加成本、延迟和方差 |
| **Gate** | 决定通过与否 | 见 3.5 |

> **每条边都是代理的图，在给自己的接线交房租。**

### 3.3 环在节点内，图在节点间

一句话解开全部混淆：**The loop lives inside a node. The graph lives between them.**

- 单元内：produce → check → correct → repeat until green
- 单元间：split、fan out、merge、gate、send back——第二个列表没有一项能从单个单元内部表达

所以你不用二选一：**没有环的图并行产出未验证的工作——比串行更糟，因为量更大；没有图的环是一个非常好的步骤，排在没人设计的队列里。**

### 3.4 两条返回路径：纠错边与学习边

没有回路的图是管线：产出输出然后遗忘，下周从同一位置带着同样的盲点重新开始。工作的图有两条返回路径：

| | 纠错边（短） | 学习边（长） |
|--|------------|------------|
| 路径 | gate 拒绝一个单元 → 回到产生它的步骤 | 被接受的结果 → 回到 **splitter** 作为约束 |
| 修的是 | **这一次运行** | **以后每一次运行** |
| 载体 | 失败原因 + 证据 | 从结果**推导出的约束**，不是输出本身 |

```
ACCEPTED   utils 切片移植完成，首过即绿
DERIVED    适配器必须精确保留关键字参数
LANDS IN   splitter 的任务简报——影响以后每一个切片怎么切
```

注意落点：**不在 worker 的指令里，而在决定工作怎么切的简报里。** 确认的原因变成规则，下一次断裂从这次结束的地方开始。

> 几乎所有人建了第一条、跳过第二条。**症状：系统很快，但永远不会更聪明。**

### 3.5 返回单元，不返回批次

返回路径上最贵的错误：四个切片移植，一个测试失败。整批打回 → 三个正确切片被重写。它们的下一版**不同但不会更好**（它们本来没错），然后四个全部重新验证，三个正确的这次可能因无关原因失败。**你把一个失败变成了四个不确定的结果，还为此付了钱。一轮里做两次，永不收敛。** 从外面看像模型反复失败——其实是返回路径在摧毁正确的工作。

随返回旅行的四样东西（每样都有职责）：

```
UNIT      handlers 切片
VERDICT   red
REASON    test_auth_redirect 失败
EVIDENCE  期望 302 实际 200，handlers/auth.py:88
SCOPE     只修这个文件，不碰其他切片
```

**SCOPE 行比看起来重要**：没有它，返回的单元会膨胀——代理打开文件、注意到两个相邻问题、顺手修了，一个切片的纠正变成没人审过的四文件 diff。

**上限三次**：一个单元失败三次纠正，问题在产生它的**计划**里——而环看不到计划。（升级到人。）

### 3.6 按爆炸半径开车道，不按置信度设阈值

多数文章建一个置信度分数、设阈值、放高分通过。**这是错误的变量。**

> 置信度是这个决策里最弱的输入，原因很容易漏看：**它是唯一能被模型影响的变量。**

强变量是「改错了会怎样」。按撤销成本分车道：

| 车道 | 例子 | 开门条件 |
|------|------|---------|
| 可逆且局部 | 文案改动、测试、有覆盖的孤立函数 | 先开——一次坏合并 = 一次 revert |
| 可逆但广泛 | 共享工具函数、schema 新增、十几个调用方 | 确定性检查 + 干净的执行轨迹 |
| **难以逆转** | 迁移、删除、写生产数据、动钱 | **这条车道不开门，无论分数多少** |

第三行不是「阈值设很高」，是**不开的车道**——区别在于：阈值会被调整，关闭的车道不会。

开门车道内，gate 按顺序读证据：**确定性结果 → 本次运行轨迹 → 该节点历史回滚率 → 模型自评（最后）。**

## 四、从哪里开始（官方顺序）

1. 拿一件你反复做的事，画出 splitter、车道、merge、一个 gate、一条回边
2. **先建 gate**——有东西能大声失败之后，一切都变容易；没有 gate 的图只是更快产出未验证输出的方式
3. 然后车道
4. **学习边最后**——在有东西接受结果之前，你无法从被接受的结果推导约束
5. **人放在一个步骤上**：后果最高、可逆性最低的那个点。批准合并、选择哪些修复上线——不审中间输出、不确认每一步

> **人在图的中间，就成为图中最慢的节点——图的运行速度恰好等于一个人读东西的速度。**

三句话撑起整个纪律：

- **度量路径，不只度量它落到的答案**
- **不改变接下来跑什么的裁决，只是报告**
- **任何你没变成永久约束的失败，你还会再遇到**

## 五、深度思考：五个问题

**Q1：官方六层与你知识库的 Harness 体系是什么关系？**
[Harness工程学习总结](/posts/obsidian/harness-engineering/) 给出公式（Agent = Model + Harness）和五层运行环境；官方这篇给出**可操作的六层清单 + 一个执行提示**。差异点值得注意：官方把 **Hooks 独立成层**（此前散在权限/验证里）——「每次编辑后自动 format/lint/typecheck、无例外」是把确定性检查从「验证时」提前到「每次动作后」，失败在最小粒度被拦截。这正是 [图工程实战 - 如何构建替代循环的代理系统](/posts/obsidian/graph-engineering-practice/) 的「硬约束在代码不在提示词」的产品级形态：**钩子就是没有提示词的约束。**

**Q2：学习边是新东西吗？**
机制不新，**落点是新的**。你库里已有三个同构物：SIM（优化器读历史修复记录）、Opik（失败锁定为回归测试）、Skill 自进化（反馈转化为检查/工具）。但本文补了一个关键细节：**学习边落在 splitter 的简报里，不是 worker 的指令里**。推导出的约束应该改变「工作怎么切」，而不只是「工作怎么做」——这比把教训写进提示词高一层。对照 [RSI 与自我提升记忆 - Harness 自修复的闭环](/posts/obsidian/rsi-self-improvement-memory/)：SIM 正是落在优化器（切分与决策者）的上下文里，两者完全一致。**教训要落在决策层，不是执行层。**

**Q3：「置信度是唯一能被模型影响的变量」为什么重要？**
这是对你已有「爆炸半径 × 可改周期」矩阵（[与AI代理协作的方式 - 2026年10月十五条实践](/posts/obsidian/ai-agent-collaboration-practices/)）的**安全性论证补全**。之前的矩阵说了「按什么分」，本文说了「为什么不能按置信度分」：门的所有输入里，确定性检查、运行轨迹、历史回滚率都是模型**伪造不了**的，唯独置信度是模型自己报的——**用模型可影响的变量做门禁，等于让被审查者给自己打分。** 这也解释了「阈值 vs 关闭车道」的区别：阈值是连续量，会被上下文、话术、甚至模型的措辞习惯推移；车道是离散的结构，模型够不到。

**Q4：「返回单元不返回批次」与 SuperPlane 的定向反馈是什么关系？**
同一条原理的两个粒度。SuperPlane 说修正运行只拿失败摘录不拿全量历史（上下文侧的最小化）；本文说打回只打失败单元不打整批（**工作侧的最小化**）。合起来：**反馈的最小作用域原则——上下文只给相关的，重做只做失败的。** 而 SCOPE 行的作用等价于 DeepSeek 的 Mandate：给修复动作一个不可膨胀的边界。没有 SCOPE 的修复会「顺手多修」，这与 [DeepSeek 超级代理设计 - 注意力经济学与领域模型](/posts/obsidian/deepseek-superagent-design/) 的「范围变宽 = 新 Ticket」是同一条纪律。

**Q5：先写检查（check-first）改变了什么建设顺序？**
它把 TDD 搬进了代理工程：**先定义失败，再构建工作**。你已有的建设顺序知识（[从 Agent Demo 到 Agent Platform - 六层工程能力深度拆解](/posts/obsidian/agent-demo-to-platform/) 的六层补建顺序、本文第四节的 gate-first）在这里汇合成一个统一排序：**gate → 车道 → 工作 → 学习边**——先有能失败的检查，再有权限结构，再有执行，最后才有进化。任何顺序颠倒都会在某个阶段付学费：先建工作 = 两个乐观主义者互相点头；先建学习边 = 没有结果可学。
