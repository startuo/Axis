## 30 秒答案

这篇文章提供了一套**从零到 GitHub 的完整 Skill 创建方法论**，核心只有一句话：

> 把"我每次都要重新解释"，变成"它以后知道该怎么做"。

八个步骤：**理解 Skill → 筛选工作流 → 写工作流卡片 → 准备触发案例 → 决定目录结构 → 初始化 → 写 SKILL.md → 验证安装 → 真实测试 → 上传 GitHub**。

但方法论本身不是重点——重点是背后的两条设计哲学：
1. **Skill 不是提示词，是岗位说明书 + SOP + 工具箱**
2. **先用纸笔想清楚工作流，再让 AI 帮你固化成文件**

---

## 一、什么是 Skill？——一个精确的心智模型

### 1.1 作者的定义

把 Codex 想象成一位**能力很强、但刚入职的新同事**。它懂写作、代码、表格和分析，但不知道：

| 它不知道的 | 对应的 Skill 职责 |
|---|---|
| 什么情况下启动某项工作 | **触发条件**（when to use） |
| 先做什么、后做什么 | **执行步骤**（how to execute） |
| 哪些规则不能违反 | **约束规则**（constraints） |
| 输出必须包含哪些栏目 | **输出格式**（output format） |
| 做到什么程度才算合格 | **质量标准**（quality criteria） |

Skill 就是交给这位新同事的：**岗位说明书 + 标准作业流程 + 必要工具和资料**。

### 1.2 与提示词的本质区别

> 普通提示词只服务当前对话。Skill 保存在固定目录中，可以点名调用，也可以让 AI 自动判断是否使用。
>
> **提示词解决一次任务，Skill 固化一类任务。**

这是一个关键的分水岭——提示词是"这次怎么做"，Skill 是"以后每次都这么做"。

### 1.3 连接已有知识：Skill 在 Harness 体系中的位置

在我之前研究的 [Harness 工程体系](/posts/obsidian/harness-engineering/) 中，Harness = Agent - Model，即模型之外的一切工程约束。Skill 正是 Harness 层的核心组件：

```
┌─────────────────────────────────────────────┐
│              HARNESS（马具层）                  │
│  ┌───────────────────────────────────────┐  │
│  │           SKILL（技能层）               │  │
│  │  触发条件 + 工作流程 + 质量标准          │  │
│  │  ┌─────────────────────────────────┐  │  │
│  │  │       PROMPT（提示词层）          │  │  │
│  │  │   单次对话的即时指令              │  │  │
│  │  └─────────────────────────────────┘  │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

Skill 不研究怎么让模型更聪明，而是研究**怎么让模型在固定的做事方式下稳定输出**——这恰好是 Harness Engineering 的核心命题。

## 二、筛选：什么工作流值得做成 Skill？——决策框架

作者给出了一个四问筛选法，这是整篇文章中最容易被跳过的内容，但恰恰是最关键的。**不要看到任何重复提示词都急着做成 Skill。**

### 2.1 四个筛选问题

| # | 问题 | 本质 |
|---|---|---|
| 1 | 这件事是不是会**重复发生**？ | 频率判断 |
| 2 | 它有没有**相对稳定的输入和输出**？ | 结构化程度 |
| 3 | 中间是否存在**固定步骤、规则或判断标准**？ | 流程化程度 |
| 4 | 如果换一个 AI，你是不是还要**重新解释一遍**？ | 可移植性 |

**三个回答"是"，就值得沉淀。**

### 2.2 适合 vs 不适合

| 适合做成 Skill | 不适合做成 Skill |
|---|---|
| 每周零散记录 → 复盘和下周计划 | 只会发生一次的临时任务 |
| 每次按同一套标准写 𝕏 长文或起标题 | 一句话就能说明白的简单操作 |
| 发布产品前的固定检查清单 | 完全依赖临场创意、无稳定步骤 |
| 审核合同时检查相同风险项 | "帮我处理所有内容"这种无边界大目标 |
| 根据品牌规则回复客服消息 | |
| 固定格式会议记录 → 任务清单 | |
| 重复处理同一类 PDF、表格或接口数据 | |

### 2.3 最容易犯的错误：一上来就做"全能内容助手"

> 范围越大，触发越模糊，执行越不稳定。
>
> "帮我做内容运营"不适合作为第一个 Skill。
> "把访谈记录整理成一篇符合固定结构的 𝕏 长文"就清楚得多。
>
> **好的 Skill，不是无所不能，而是能把一件具体的事稳定做好。**

这条原则与 Super Powers 的 "为低水平执行者设计"（[Harness工程学习总结](/posts/obsidian/harness-engineering/)）高度吻合——你必须假设执行的 Agent 是一个热情但缺乏判断力的执行者，所以范围必须窄到它不会走偏。

## 三、八步工作流：从纸面到 GitHub 的完整路径

### 第一步：把脑子里的工作流写到纸面上——「工作流卡片」

**核心原则：先不要建文件，先用纸笔把工作流想清楚。**

工作流卡片的六要素：

```
工作流名称：

什么时候启动：

用户会提供什么：

执行步骤：
1.
2.
3.

最后输出什么：

什么结果算合格：

信息不足或出错时怎么办：
```

**以"每周复盘"为例：**

```
工作流名称：把一周的零散记录整理成复盘

什么时候启动：用户提出周报、每周复盘、一周总结或工作回顾时

用户会提供什么：一周内完成的事情、问题、数据和下周计划

执行步骤：
1. 提取事实和数据
2. 分类为成果、进展、问题和经验
3. 合并重复内容
4. 把未完成事项转成下周行动
5. 检查是否存在编造或空话

最后输出什么：结构化周复盘和下周行动表

什么结果算合格：保留原始数据；不虚构；行动有优先级和完成标准

信息不足时怎么办：标记"待补充"，最多提出 3 个问题，不要猜
```

作者特别强调：**如果你填不完这张卡片，说明这件事还没有形成稳定工作流。** 这时应该先多做几次，记录自己每次如何判断，再回来做 Skill。

> 不要把混乱包装成 Skill，先把工作流本身想清楚。

这呼应了 [GSD 的 Artifact 思维](/posts/obsidian/harness-engineering/)——持久化的结构化中间产物是稳定性的基础。

### 第二步：准备 3 个真实触发案例

三句话覆盖三种场景：

| 案例 | 示例 | 测试目标 |
|---|---|---|
| 明确点名 | `请使用 $weekly-review 整理这周的记录` | 点名后能否正确执行 |
| 自然表达 | `帮我把这些流水账整理成周报，再列出下周优先级` | 没点名时能否自动触发 |
| 信息不完整 | `这周主要在做支付功能，帮我复盘一下` | 信息不足时会不会乱编 |

> 很多人只写"这个 Skill 能做什么"，却没有想过"用户会怎么说"。
>
> 触发案例不是宣传文案，而是 Skill 的入口测试。

### 第三步：决定 Skill 里要放什么——最少必要结构

**最小可用版本只需要一个文件：**

```
your-skill/
└── SKILL.md
```

**比较完整的结构：**

```
your-skill/
├── SKILL.md          ← 必需：触发条件、工作步骤、质量标准
├── agents/
│   └── openai.yaml   ← 推荐：界面中的名称、简介和默认提示
├── scripts/          ← 需要稳定执行的代码（格式转换、数据校验）
├── references/       ← 长资料（公司规则、术语、接口文档）
└── assets/           ← 模板、图片、字体等交付素材
```

**决策树：**

| 情况 | 行动 |
|---|---|
| 只有文字流程 | 先写一个 SKILL.md |
| 同一段代码每次都要重写 | 放进 scripts/ |
| 背景资料很长，不是每次都要读 | 放进 references/ |
| 每次交付都要套相同模板 | 放进 assets/ |

> 不要为了显得专业，先建立一堆空目录。Skill 会占用上下文，应该只保留完成任务真正需要的内容。
>
> **先做最小可用版本，用到什么再增加什么。**

这个"按需增长"的哲学，本质上是一种**增量实现（incremental implementation）**策略——与 [Super Powers 的 Empirical Skill Engineering](/posts/obsidian/harness-engineering/) 中的 RED-GREEN-REFACTOR 循环一致：先让它在真实任务中跑起来，再根据失败点改进。

### 第四步：让 Codex 初始化 Skill

关键规则：
- 名称只使用**小写英文字母、数字、连字符**，不要空格和中文
- 文件夹名和 Skill 名保持一致
- 新手最简做法：直接把工作流卡片发给 Codex，让它调用 `skill-creator`

```
请使用 skill-creator，把下面的工作流做成一个 Skill。

Skill 名称：weekly-review

工作流：
[粘贴你的工作流卡片]
```

生成的结构：
```
weekly-review/
├── SKILL.md
└── agents/
    └── openai.yaml
```

### 第五步：写好 SKILL.md——执行手册的骨架

这是整篇文章中最具操作性的部分。SKILL.md 分为 YAML 头部和 Markdown 正文。

#### 5.1 YAML 头部决定"什么时候触发"

```yaml
---
name: weekly-review
description: 将一周的零散记录整理成结构化复盘和下周行动计划。用户提到周报、每周复盘、一周总结、工作回顾、学习复盘，或要求从流水账中提炼成果、问题、经验和下一步行动时使用。
---
```

`description` 必须同时回答两个问题：
1. 这个 Skill 能做什么？
2. 用户在什么场景下应该使用？

**反例：** `帮助用户复盘。`——没有具体场景。
**正例：** 把"周报、每周复盘、一周总结、流水账"等真实触发方式写进去。

> Codex 会先读取 name 和 description 判断是否触发，然后才会读取正文。所以"什么时候使用"要写在 description 中，不要藏在正文最后。

#### 5.2 正文决定"触发后怎么做"

作者推荐的通用结构：

```markdown
# Skill 名称

用一句话说明目标。

## 工作流程
1. 收集并检查输入
2. 按固定规则处理
3. 生成结果
4. 检查结果

## 信息不足或异常时
- 缺少重要信息时怎么处理
- 哪些内容不能猜测
- 什么时候应该停止并询问用户

## 输出格式
[固定栏目、顺序或模板]

## 质量标准
- 必须包含什么
- 不能出现什么
- 怎么判断已经完成
```

**写正文的三条原则：**
1. 只写完成任务必须知道的内容
2. 越容易出错的环节，规则越要具体
3. 能用 30 行说清楚，就不要写 300 行

> Skill 不是知识百科，而是执行手册。

### 第六步：验证并安装

```bash
# 验证格式
请使用 skill-creator 验证 ./weekly-review

# 安装到 Codex Skill 目录
cp -R ./weekly-review ~/.codex/skills/
```

验证器只检查结构（文件夹名一致、YAML 格式正确、name/description 存在、命名合规），**它不保证工作流本身好用**。

在我的 vault 中，Codex Skills 路径：`<本地用户目录>`（参见 Skills 索引）。

### 第七步：拿真实工作测试——三轮验证

回到第二步准备的三个案例：

| 测试轮 | 输入 | 检查点 |
|---|---|---|
| 测试 1：明确点名 | `请使用 $weekly-review 整理下面的记录` | 是否按 Skill 规定的栏目和顺序输出 |
| 测试 2：不点名 | `把这些流水账整理成周报，再列出下周优先级` | description 是否足够让 AI 自动识别 |
| 测试 3：信息不完整 | `这周主要在做支付功能，帮我复盘一下` | 是否标记缺失信息，而非虚构数据 |

**结果不理想时的诊断框架：**

| 症状 | 根因 | 修复方向 |
|---|---|---|
| 没有自动触发 | description 不够具体 | 把真实触发说法写进 description |
| 执行顺序不稳定 | 工作流程不够明确 | 增加步骤编号和强制检查点 |
| 总是出现空话 | 质量标准太模糊 | 增加具体动词要求和禁止词汇表 |
| 信息不足时乱编 | 缺少异常处理规则 | 增加"标记待补充，最多提 3 个问题" |
| 同一段代码反复生成 | 可执行逻辑没固化 | 把它放进 scripts/ |
| SKILL.md 越写越长 | 长资料没分离 | 把参考资料放进 references/ |

> 测试的目的不是证明第一版正确，而是找到下一次应该改哪里。

这与 [Karpathy 的环路工程](/posts/obsidian/karpathy-loop/) 中的评估驱动迭代完全一致：每次运行 → 观察失败 → 精确修复 → 重新验证。

### 第八步：上传到 GitHub

GitHub 提供四个价值：
- **备份**工作流
- **记录**每次修改（版本控制）
- **多设备同步**
- **分享**给团队或粉丝

**安全检查清单（公开前必做）：**
- [ ] 删除 API 密钥和 Token
- [ ] 删除密码和账号
- [ ] 删除客户数据和公司内部地址
- [ ] 删除未公开的业务规则
- [ ] 不确定时先使用 Private 仓库

```bash
git init -b main
git add .
git commit -m "feat: add my first Codex skill"
git remote add origin <仓库地址>
git push -u origin main
```

## 四、新手最容易踩的 5 个坑——反面教材

| # | 错误 | 正确做法 |
|---|---|---|
| 1 | 把聊天记录直接塞进 SKILL.md | 先提炼触发条件、步骤、异常处理和验收标准 |
| 2 | 一个 Skill 想解决所有问题 | 先从一个明确输入、一个明确输出开始 |
| 3 | 只有步骤，没有完成标准 | "包含 5 个固定栏目，每个行动有优先级和完成标准"才是验收标准 |
| 4 | 验证通过就认为完成 | 验证器只检查结构，真正质量靠三轮测试 |
| 5 | 把敏感信息上传到公开仓库 | 不确定时用 Private |

## 五、深层方法论提取：超越"怎么做"的"为什么"

### 5.1 Skill 设计的核心张力：范围 vs 稳定性

```
范围大 ────────────────────────────→ 范围小
  触发模糊                            触发精准
  执行不稳定                          执行稳定
  "帮我做内容运营"                    "把访谈记录整理成 𝕏 长文"
```

作者的选择很明确：**牺牲范围，换取稳定性。** 这与 [Super Powers 的 1% Rule](/posts/obsidian/harness-engineering/) 设计哲学一致——宁愿过度触发（范围小 + 条件清晰），也不要漏触发（范围大 + 条件模糊）。

### 5.2 三层抽象：提示词 → Skill → Harness

```
提示词（Prompt）    → 解决"这一次"     → 即时消费，用完即弃
Skill               → 解决"这一类"     → 持久存储，可点名、可自动触发
Harness             → 解决"整个系统"   → 流程门禁、上下文路由、多 Agent 编排
```

Skill 处于中间层——它比单次提示词更持久，但不像完整 Harness 那样需要系统级工程。它是**个人工作流沉淀的黄金单位**。

### 5.3 对抗性设计思维

文章中反复出现的模式是**假设 AI 会出错，然后提前堵住**：

- 填不完工作流卡片 → 说明工作流还没稳定，不要强行做成 Skill
- description 写得不具体 → AI 不会自动触发
- 没有异常处理规则 → AI 会虚构数据
- 没有质量标准 → AI 会输出空话
- 验证器通过 ≠ 工作流好用 → 必须拿真实任务测试

这与 Jesse Vincent（Super Powers 作者）的 **Empirical Skill Engineering**——观察 Agent 在哪里失败，分析它用什么借口跳过规则，然后改写 skill 堵住这个借口——完全一致。

### 5.4 "纸笔先行"原则

作者反复强调：**先不要创建文件。**

工作流卡片 → 触发案例 → 再让 skill-creator 生成。这个顺序不是随意的，而是防止"文件结构依赖"——当你先建了一堆目录后，你会倾向于把内容塞进去，而不是先想清楚内容本身。

> 第一版不需要完美。先让它在一个真实任务中跑起来，再根据结果修改。

这是 **MVP + 迭代** 方法论在 Skill 设计中的直接应用。

## 七、行动框架：我今天就能用的检查清单

### 即学即用的 Skill 创建检查清单

```markdown
## Phase 1: 筛选
- [ ] 重复发生 ≥ 2 次
- [ ] 有稳定输入输出
```

## 八、核心提炼：一段话记住全部

> 找到你最近一个月跟 AI 重复解释过两次以上的任务，填一张六行工作流卡片（什么时候启动、用户提供什么、执行步骤、最终输出、什么算合格、信息不足怎么办），准备三句用户可能说的话，让 skill-creator 生成第一版，装到 `~/.codex/skills/`，用那三句话逐个测试。哪里失败改哪里，跑通后 push 到 GitHub。
>
> 核心只有一句：**把"我每次都要重新解释"，变成"它以后知道该怎么做"。**
