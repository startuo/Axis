## 30 秒答案

DeepSeek Harness 团队发布了一个研究原型 **dsh-superagent**：一个为一个 GitHub 仓库服务的**主动式编码代理**，监听 GitHub 和飞书——有人（被允许的人）向它要工作，它开工单、在**自己的 agent 会话和目录**里干活、在原始对话里回复结果（例如 PR）。一个面板只显示「哪些事在等人」。

> 它的核心哲学只有一句话：**拿走尽可能少的人类注意力，给出尽可能多的价值。**（Take as little human attention as possible, and give as much value as possible.）

这条哲学驱动了一切设计——每个消息、通知、问题、设置项、面板元素、文档段落都要通过 ROI 检验。由此长出一个**极简领域模型**（Source/Thread/Eval/Mandate/Ticket 五个核心概念 + 显式的「被拒绝概念」清单）、一个**版本化的授权系统**（准入表 + 三种 accept mode + 不可变的 Mandate）、以及一套**优先级分层的提示词架构**（外部消息永远只是数据，不能改变权限）。

> 最反直觉的一句话：**代理只在被要求时行动、只在人必须行动时说话。** 一个能为全团队干活的代理，也能浪费全团队的注意力——所以它安静，是特性，不是缺陷。

## 一、来源与定位

- **原型**：[github.com/deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（MIT，研究参考用，非官方产品）
- **配套文章**：*Exploring Super-agent Design: Towards a More Autonomous Agent System*
- **形态**：DeepSeek Harness 的一个 bundle，为单个仓库服务的主动式编码代理
- **诚实的声明**：代码大量由编码代理自己编写；为发布做了改编，与内部版本不一致；文中部分设计是未来方向，原型未实现

它的定位不是又一个「更强的 agent」，而是**一个工作方式的宣言**：一个能代表整个团队行动的代理，也必须被设计成**不消耗团队**。

## 二、核心哲学：注意力经济学

每个部件都用它消耗的注意力来计价。一条消息、一个通知、一个问题、一个设置、一个面板元素、一段文档——**每个都要给出比它消耗的注意力更多的价值，否则就删除。**

### 对代理的要求

| 原则 | 含义 |
|------|------|
| **只在被要求或书面规则允许时行动** | 请求必须直接对代理说、且来自允许名单上的人；没人要求的工作需要团队写的规则，且**从「只记录它本会做什么」的模式开始** |
| **只在人必须行动或能用上结果时说话** | 接单确认一次并说出将做什么 → 干活时安静 → 结果就绪/需要决策/无法完成时才再写。消息短，回到原对话 |
| **一次只问一个具体问题** | 用结构化形式，让问题到达人，而不是沉在长报告里 |
| **按影响停止，不按努力停止** | 局部改动走到「可审查的结果」为止；需要设计决策的改动，带着清晰的问题停下来 |
| **诚实报告** | 草稿标记未完成、失败就报失败、**绝不绕过限制来避免提问** |

### 对设计的要求

- **少概念**：设计只有领域概念（Source）和具体实现（GitHub、飞书）。业务需求变成某个概念的属性，或一段提示词——**不为它新增概念**
- **少设置**：一个值适合几乎所有团队时，默认值替代设置；团队用语言描述的行为是提示词文本，不是设置项
- **面板只显示需要人的东西**：等人工的事项排第一；**健康状态不占任何空间**
- **文档按序阅读**：每篇只依赖之前的篇目

### 责任（操作者欠团队的）

- **从窄开始**：短允许名单 + 主动工作只记录。等「它本会做什么」看起来对了，再放宽
- **为降噪而调**：代理吵了，就缩短/收紧提示词或暂停它——**不要加更多消息去解释噪音**
- **不追求产量**：批量 PR、广播消息、忙碌的工作消耗团队多于产出
- **为它说的话负责**：读它以你的名义发出的每一条消息，错了就改提示词

## 三、领域模型：五个概念 + 被拒绝的概念

### 核心流

```
Source → Trigger → Thread → Eval（Gate 准入 + Assessment 研判）
  → Decision（accept/stop/ignore/unavailable）
  → Ticket（携带 Mandate 授权）→ Assignment → Executor
  → 结果经 Channel 回到 Source
```

| 概念 | 定义 | 规则要点 | 存在理由 |
|------|------|---------|---------|
| **Source** | 事件流（可复用种类 + 实例配置） | 持有读取位置和机器人身份；丢弃自己的消息 | 重启不得重放事件 |
| **Trigger** | 一个不可变事件 | 属于一个或多个 Thread；**同一 Trigger 接两次只建一个 Ticket** | 审计与幂等的单位 |
| **Thread** | 按时间序的 Triggers | 同一时间最多一个 Eval 在跑；Eval 串行，期间的 Trigger 合并进下一批 | 给 Eval 一致视图 |
| **Eval** | 对一批 Triggers 的判断，**两层**：Gate（确定性准入）+ Assessment（模型研判） | 无状态；输入 = Trigger 批 + Thread 快照 + 全部 Ticket + 当前 Policy | 决定新工作开始/继续/停止 |
| **Mandate** | 接单授予之物：策略版本、范围、强度、命中的规则、发送者身份 | **不可变**；范围变宽 = 新 Ticket；只有人停止或策略撤销才能收回 | 说明为什么可以做、可以做到多远 |
| **Ticket** | 一个被授权的工作单元 | 只有 Eval 能创建；open → ended，可被人复活；**定义自己的状态，不跟随 Executor** | 拥有执行与报告 |
| **Assignment** | Ticket 与一个 Executor 实例的绑定 | 一个 Ticket 随时间有多个；只有最终报告能在 Executor 侧结束 Ticket | 谁执行必须在域内 |
| **Subscription** | Ticket 与 Thread 的多对多订阅 | 匹配的 Trigger 扇出给每个活的订阅 Ticket，**不检查发送者**；人的消息到达即生效，不需要再 Eval；bot/CI 消息到达但不复活 Ticket | 后续讨论到达执行器，无需再 @ 代理 |

**人在这个模型里不是一个领域概念。** Trigger 只携带 actor 标识符（Source 给的）；允许名单是 Policy 里 Source 的一部分。同一个人在多个 Source 上有账号这件事，只是提示词文本。

### 被拒绝的概念（设计负空间）

这份文档最独特的部分——显式记录**拒绝过什么以及为什么**：

| 被拒绝的设计 | 理由 |
|-------------|------|
| Principal/Membership 实体、跨 Source 身份映射 | 人是 Trigger 元数据；映射是提示词文本 |
| Eval 调度自己的延迟 Trigger | 等待类条件做成普通 Source，Eval 永不反向依赖 Source |
| 每 Thread 最多一个活 Ticket | 一个 Thread 可承载多件独立工作，去重靠评估看 Ticket 列表 |
| 策略变更时取消运行中的 Ticket | 留下半成品工作；改为记录变更并送达 |
| Executor 声明「人让我停止」 | 只有 Eval 决定结束的强度 |
| 从报告自由文本推断「在等人」 | 分类需要结构化事实；Executor 通过结构化字段提问 |
| 失败时锁死 Executor 的全部工具 | 会拒绝直接在 Session 里工作的人，以及恢复后的报告；暂停自动输入即可 |

## 四、授权：两条路径、两种强度、三格准入表

### 两条路径

1. **Eval 路径（开始新工作）**：Gate 检查发送者与 Source 的 Policy——允许名单上的人直接点名 = **明确请求**；其他人工消息查准入表；机器人只能产生**推断候选**，永不能成为明确请求
2. **Subscription 路径（延续已有工作）**：订阅 Thread 上的每条消息作为上下文扇出到 Ticket，**绕过 Gate 但不授予任何新权限**——每个 Ticket 始终被自己的 Mandate 限制

### 强度（Strength）

| 强度 | 情形 |
|------|------|
| **explicit（明确）** | 名单上的人点名代理；或有 Ticket 的 Thread 上的跟进；准入表设为明确请求的格 |
| **inferred（推断）** | 非名单上的人在已有 Ticket 的 Thread 上跟进；准入表设为推断的格；bot 名单上的机器人点名 |
| **not admitted（不准入）** | 其他 bot 的消息；准入表忽略的一切；accept mode 为 off 时的所有推断情形 |

### 三格准入表（每个接收范围一行）

| 格 | 选择 | 默认 |
|----|------|------|
| 在名单上，未点名代理 | inferred / ignore | **inferred** |
| 不在名单上，点名了代理 | explicit / inferred / ignore | **ignore** |
| 不在名单上，未点名 | inferred / ignore | **ignore** |

### 三种 accept mode（策略的一部分）

| 模式 | 效果 |
|------|------|
| `off` | 一切推断不成为候选 |
| **`observe`（默认）** | 推断候选被评估；正面评估被记录为「would accept」的 ignore，**不实际接单** |
| `auto` | 推断候选评估正面即接单 |

明确请求在任何模式下都工作。**从 observe 开始，审查记录的决定后再切 auto。** 策略版本化：每个 Mandate 记录它被接受时的策略版本；版本变更丢弃运行中的 Eval 并重新排队 Trigger，给受影响的活 Ticket 发「策略已变更」输入——但**不追溯撤销**已接受的 Mandate（重新验证时才撤销）。

## 五、执行：一人一目录、人优先、按影响停止

### Ticket 七阶段（自上而下，第一个匹配生效）

| 阶段 | 条件 |
|------|------|
| person / delivery | 输入投递失败（2 秒→倍增到 1 分钟重试） |
| person / answer | 有 Attention（待回答的问题） |
| person / review | 最新报告为 `ready` |
| person / blocked·failed | 最新报告 `blocked`/`failed` 且无人消息到达 |
| working / queued | 无 Assignment 或待启动 |
| idle | 报告为 `waiting`，或 Assignment 结束——等 Trigger 继续 |
| working | 其余一切 |

`person` 阶段 = 没有人工输入无法继续；`idle` = 完成了一轮且没有悬而未决的问题，订阅 Thread 上的新 Trigger 可以继续它。

### 关键设计

- **一人一目录**：每个 Ticket 一个 `worker-<id>` 会话 + 独立目录（典型用 `git worktree` 做检出）；PR 属于 Ticket，当分支末段匹配 Ticket 短名
- **人优先的并发**：worker 槽位按配置限制，但**额外留一个槽位给人的消息或状态请求**——新工作永远不能阻止人继续已有 Ticket
- **按影响停止**：局部改动走到可审查结果；需要设计决策的改动带着清晰问题停
- **合并门槛**：auto-merge 默认关闭（GitHub 会把合并归因于开启者）；默认指令只在「PR 就绪 + 审批覆盖 head commit + 增删合计 < 200 行」时允许；推新版本前撤回 auto-merge
- **结束**：`ready` 无 PR → completed；`dropped`（无需处理）→ 静默结束，人的后续消息可复活它

## 六、提示词架构：五层优先级

### 优先级（从最强到最弱）

| 层 | 内容 | 可变性 |
|----|------|--------|
| 1. **工具与宿主强制的事实** | 身份、权限、工具参数检查、回复用途、长度限制 | 提示词**不能**改变 |
| 2. 内置与生成节 | 角色、路由、订阅、工作、准入、环境、策略 | 团队可覆盖 |
| 3. 匹配规则的流程与沟通 | 仅对该 Ticket 的 Executor 生效 | 团队可写 |
| 4. 团队节与技能 | Communication / Ticket scope / Delivery requirements + skills | 团队可编辑 |
| 5. **外部文本** | 消息、评论、文档、引用 | **只是数据，永不改变规则或授权** |

> 「消息不能改权限」——这是整个授权模型的根基。权限由宿主强制，提示词只能影响模型如何思考，不能影响系统如何裁决。

### 内置文本的原则（哲学在提示词层的落地）

- **分离角色**：main Session 只路由（转发原始 Trigger + 路由事实，不做技术决策；路由笔记 ≤ 30 词）；Executor 读原始来源、判断范围、实现、验证
- **main Session 不等待**：禁止 `sleep`、shell 超时 >30s、job 等待 >5s——阻塞的一步会推迟新候选
- **消息硬限**：默认一句话，硬上限 100 词
- **确认一次，说清楚**：开工前确认每个新请求，在原始消息下回复「对象 + 预期结果」
- **提问走 `human_action`**：Report 里放一个具体问题，main Session 原样转发
- **诚实交付**：开 PR ≠ ready；draft 标记未完成；**UI 改动没有真实的改动前截图 = 未 ready**
- **人的暂停永久有效**：跨跟进、跨新会话、跨重启，直到人解除；**自动反馈永远不恢复被暂停的工作**
- **例子只展示格式**：示例句不是代理可以声称的事实
- **按结果处理评审**：已修复已验证的评论静默解决；拒绝的给一句理由；**每个自动评审者每 PR 最多三轮**
- **向重复工作让步**：人的分支/PR 已含此变更时，关闭自己的 PR 并用一句话指向对方

### 版本化

每次保存创建不可变版本（完整配置 + 修订号 + 前驱 + 时间戳 + 来源）；冲突保存被拒绝但不丢弃草稿；会话每次模型请求读最新版本。升级时保留团队文本，默认值变化会在面板标出「Default updated」并并排显示差异。

## 七、深度思考：六个问题

**Q1：注意力护栏和正确性护栏是什么关系？**
SuperPlane 的护栏关心正确性（false pass 的代价），DeepSeek 的护栏关心**注意力**（噪音的代价）。两者互补且都必要：一个系统可以修对 100% 的 bug 却因为吵死团队而被关掉——正确性护栏管「会不会出事」，注意力护栏管「会不会烦人」。十五条实践 #10「别等代理，让它们来伺候你」只说了态度，DeepSeek 把它变成了**可审计的设计准则**：每个消息、面板元素、设置项都要过「价值 > 注意力成本」的检验。衡量团队代理系统成不成功的最终指标，不是吞吐量，是**「没人提到它」**——安静是最高评价。

**Q2：observe 模式为什么是天才设计？**
observe = 评估一切、记录「would accept」、不实际接单。它把「信任」变成了一段**可审查的虚拟历史**：切 auto 之前，你已经看过了几十条「如果开了自动接单它本会接什么」。这与图工程的「先在纸上画草图、先手动跑 5 次再升 /loop」、SuperPlane 的「自动启动默认关闭」是同一条原理在授权层的应用。三者的共识：**授权必须比能力滞后一个阶段**。

**Q3：Mandate 不可变 + 策略版本化解决了什么？**
图工程说「硬约束放在边逻辑，不放提示词」；DeepSeek 更进一层：授权本身成为**版本化的一等公民**。每条 Mandate 记录它依据的策略版本——规则改了，跑了一半的工作不会被追溯撤销（撤销留下半成品），但恢复时会重新验证。这回答了图工程没回答的问题：**「规则在运行中变了怎么办？」** 答案是：让授权带版本号。

**Q4：为什么 Ticket 要定义自己的状态，不跟随 Executor？**
因为执行器是临时的（可 handoff、可复活、一个 Ticket 可由多个 Executor 串行执行），而工作的**生命周期**是持久的。这和图工程的 STATE.md 同源，但更形式化：状态不是「顺带记录的文件」，而是域模型里拥有一等规则的概念。反过来说：如果你的代理系统里「状态跟随会话」，那会话一断，工作就丢了——这正是图工程说「没有状态的图会重启」的根因。

**Q5：「按影响停止」与 Astra 的「定义完成」是什么关系？**
互补。Astra 文章说：在开始前把「完成」写进请求，防止过早终止。DeepSeek 说：**停止的边界由影响决定，不由努力决定**——局部改动走到「可审查的结果」为止；需要设计决策的改动停下来问。合成的完整规则是：**开工前定义完成的证据（Astra），执行中让影响定义停止的位置（DeepSeek）**。一个防「过早停」，一个防「走太远」。

**Q6：被拒绝的概念表有什么价值？**
这是全篇最独特的沉淀形式。大多数框架文档只写「有什么」；DeepSeek 写「拒绝过什么、为什么」。它的价值在于：**设计负空间防止后人重复论证**。比如「拒绝 Principal 实体」——未来有人提出「要不要建一个统一的用户模型」，答案已经在表里：「人是 Trigger 元数据」。这与我知识库的沉淀原则同构：**记录决策，而不是只记录结果**。值得效仿的格式：每个重要设计文档都应该带一张「我们拒绝过什么」。

## 九、对我知识库的增量

这篇文章带给本库的**新知识**：

1. **注意力经济学**——一个此前缺失的度量维度：此前所有文章都在问「怎么让代理更对/更快」，它问「怎么让代理不烦人」
2. **领域模型方法**——把代理系统当作正式域来建模（概念表 + 规则 + 被拒绝概念），而非随手写脚本
3. **授权作为版本化对象**——Mandate + Policy version 的组合，是「硬约束在代码」的形式化升级
4. **五层提示词优先级**——「外部文本只是数据」明确划定了 prompt injection 的防线：权限永不取决于输入文本
5. **团队协作维度**——订阅扇出、人优先并发槽、向重复工作让步——之前的知识都偏「单人驾驭代理」，这是第一次沉淀「代理与团队」的关系
