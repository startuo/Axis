## 30 秒答案

编码代理已经把「编码」解决了，慢的部分是**围绕编码的一切**：决定交出什么、让检查通过、知道何时停下来。SuperPlane 1.0 的回答是：把这些决定**写成工厂，而不是每次会话重复做**。

> 工厂拥有整个过程，代理人在工厂内执行工作。护栏放在**前面**（Backlog 信心评分）和**验证环**（确定性检查 + 重试上限 + 人工升级），而不是只放在末端的 PR 审核。

四个阶段：**Backlog**（导入 issue → 3/3 信心评分 → 决定是否适合代理）→ **Implement**（代理改码开 PR）→ **Verify**（先跑确定性检查，失败定向反馈给代理，N 次后停止）→ **Done**（定义完成、更新系统、留档）。

核心洞察一句话：**你的自动化程度 = 你把它写成了工厂还是聊天。**

---

## 一、问题：编码代理仍然需要「照看」

现在的代理工作流长这样：你指向问题，Claude Code 或 Cursor 读仓库、改文件、跑测试——**好吧**。然后你花一个小时照看它：

- 检查这次的 PR 是否合适
- 打开 PR，等 CI
- 把失败的测试粘回去
- 看评论，把评论粘回去
- 自己决定什么时候放弃

> 那不是自动化。那是**你在管理一个非常快的实习生**的项目管理。

SuperPlane（[github.com/superplanehq/superplane](https://github.com/superplanehq/superplane)）就是对这块空白的开源解读——自称「一次性工程的开源工厂」：处理范围明确的积压问题，运行编码代理，用真实检查验证结果，把失败反馈给代理，最后给你一个**可审查的拉取请求**。它 2026 年 10 月发布了 1.0，把通用工作流工具收窄到这一件事上。

## 二、心理模型：工厂，不是聊天机器人

先澄清「one-shot」的含义。文档明确说：**不是给模型一个提示就完全信任**。「一次性」指的是**工程过程**的一次性：

| 维度 | 含义 |
|------|------|
| 清晰输入 | 一个范围明确的 issue |
| 受控路径 | 固定的四阶段流水线 |
| 可见结果 | 可审查的 PR + 完整执行历史 |
| 人只出现在判断点 | 只有需要判断时才用人 |

工厂由五类资源组成：**Backlog、Implement、Verify、Done、Run**。最值得关心的是 **Run（运行）**：每一步都保留事件历史、状态和重试后的伪影——所以**失败的运行可以续跑，不需要手动重建上下文**。这是代理长任务的隐痛：一旦会话断了，上下文就没了。

---

## 三、工厂的四个阶段

| 阶段 | 做什么 | 自动化 |
|------|--------|--------|
| **Backlog（待办）** | 导入 issue、丰富信息、评估是否适合代理 | 监听 GitHub Issues，规划新任务，打分 |
| **Implement（实施）** | 代理修改代码、打开 PR | 运行编码代理（Claude / Cursor / OpenAI / OpenRouter / Perplexity 可选模型） |
| **Verify（验证）** | 检查和复核，决定 PR 是否 ready；失败返回实施 | 处理 PR 评论、评分合并信心、重试环 |
| **Done（完成）** | 定义完成、更新连接系统、记录 | PR 合并时关闭任务 |

实施阶段的限制值得注意：**同时 5 次并发运行、每次 60 分钟上限**（含设置）。也可以把 PR 留在草稿状态，直到你标记 ready。

代理环境单独配置：装依赖的设置步骤、用于克隆上下文的额外仓库、工作中可调用的 MCP 服务器。像「合并信心」这样的自动化以**画布（canvas）**形式构建——触发器与动作组成可视节点图，而不是散落在别人仓库点文件里的 shell 脚本。

## 四、护栏前置：Backlog 是第一个护栏

**大多数设置把护栏放在末端（人工审核 PR），SuperPlane 把护栏放在前面。** 这一条改变了我对生产中代理的看法。

Backlog 阶段评估「代理能高度自信处理哪些问题」，其余留给团队。强力候选 issue 具备：

- 一个**有针对性的结果**
- 仓库和 issue 背景**说得够多**
- **小而有界的**表面积
- 能确认结果的**测试、检查或标准**
- 人员在合并前检查变更的**安全点**

落地为**三分制评分**：每个 issue 检查三项——**清晰度**（结果、范围、完成标准确定了吗？）、**复杂性**（适合一次运行吗？）、**可验证性**（测试能证明有效吗？）——每项附一句理由。3/3 → 任务 ready（默认仍需手动点启动，除非开自动启动）。评分不过时，代理**不猜测**：它会说是什么在阻挡，并问问题。

**深度思考**：护栏前置解决的是「决定成本」问题。末端审核模式的缺陷是：每一个不适合代理的任务都要**先被代理做一遍、再被人发现不合适**——浪费一次完整运行。前置评估把这个成本从「一次失败运行」降到「一次评分」。更关键的是，「安全委派」的定义写在 Backlog 自动化里**一次**，而不是每次有人开特工会议时重新决定一遍——这是团队级的知识固化。

## 五、Verify 才是真正的护栏所在

如果只取一节，就是这节。六条实践：

### 5.1 确定性证据优先

构建、测试、类型检查、lint、策略检查**在任何模型被要求判断之前**运行。它们稳定、可重复、成本低廉。这些就是仓库真实的 CI 检查——SuperPlane 默认在**连续 3 次失败**后暂停自动修复，通过检查会重置计数。

### 5.2 代理审核员只在必要时用

只有当需求**无法简化为命令**时才动用模型判断。用的时候给它：原始任务、当前 diff、**一个聚焦的评分标准**，并要求返回其他节点可路由的**结构化发现**——不是开放式观点。

默认的「合并置信」自动化正是这样：两节点画布（PR 触发器 → 代理按固定五分标准评分）。触发时机：PR 开启、新提交、重新打开、准备审核（跳过草稿，只评工厂自己产出的 PR）。评分标准五项：**爆炸范围、性能、安全性、偏离规格、可逆性**——和我之前沉淀的「审查四问」几乎是同一个思维。

### 5.3 定向反馈，不是全量历史

修正运行只拿到：触发检查或注释、**相关的失败输出**、当前 PR 和分支、原始任务边界、下一个必须通过的检查。**不是整个执行历史。** 上下文更少 → 修复更好 → token 更省。

### 5.4 PR 评论也过同一个门槛

由你决定：人类是否必须标记 `@superplaneagent` 才能触发修正、它应该听哪些机器人。

### 5.5 绑定环：重试上限 + 人工升级

修正后 PR 回到必要的检查。上限由你设定。当**同一检查屡屡失败、反馈与原始范围冲突、或评审要求产品决策**时，任务交给真人。

> 这是人们自己给代理接线时最常跳过的护栏。**没有重试次数和升级路径的代理，会在不稳定的测试上永远烧掉 token。**

重试限制不是隐藏设置，就是出厂默认里的一个环路节点：

```yaml
- id: ci-loop
  name: Checks Loop (max 5)
  component: loop
  configuration:
    maxIterations: 5
    timeoutSeconds: 21600
    untilExpression: $["Wait for PR Checks"].data.result.status == "success"
```

每轮迭代等待 PR 检查；失败则 Claude Code 步骤尝试修复；**检查变绿或 5 次尝试后停止**。仍失败时，画布在 PR 上显示「5 次尝试后仍然失败」然后停手。循环组件默认 10 次、最多 100 次，每个画布可调。

## 六、设置三步走

### 第一步：找一个工作空间

两条路：

| | 云（Claude 托管） | 自托管 |
|---|---|---|
| 门槛 | 注册 superplane.com，入职时连 GitHub 仓库，<5 分钟 | Docker Compose 单机版（Apache 2.0）：Linux VM（amd64/arm64）+ Docker Engine + Compose v2 + 可控主机名 + 80/443 开放 |
| 安装 | — | `VERSION=v1.0.0-rc7` → curl 下载 `superplane-single-host.tar.gz` → `./install.sh`（会要主机名、生成密钥、拉镜像、申请 HTTPS 证书） |
| 资源预算 | 无 | **每个并发 runner：2 vCPU / 8GB 内存 / 30GB 磁盘**。默认暖 1 + 最大 5 并发 = 全速 10 vCPU / 40GB / 150GB，另加核心服务。可用 `SUPERPLANE_RUNNER_MAX_CAPACITY` 和 `WARM_CAPACITY` 调低。K8s + Terraform 支持 AWS/Azure/GCP |

DNS 先查：`dig +short superplane.example.com A @8.8.8.8`。装完五项服务起在主机名下，最后几行显示 runner 容量。

### 第二步：选对第一个仓库（比配置更重要）

官方快速入门里有一节我希望**每个代理工具都附带**——「不要给代理什么」：

- ✅ 首战任务：修小 bug、更新文档、修失败测试、更新依赖、小代码改进
- ❌ 以后再说：架构重设计、大型开放式功能、任何需要产品决策的事
- **必须选已有测试或 CI 的仓库**——整个系统依赖确定性检查，没有测试的仓库给 Verify 阶段提供了无可支撑的依据

连接 GitHub Issues 后，入职程序导入最近的未结 issue 并逐个审核资格。几秒后就收到工单；代理在写代码前先**探索仓库并大声推理范围**（示例中还主动指出沙盒运行不受信任 PR 代码的安全风险、建议缩小任务范围）。token 支出和成本显示在顶部。

### 第三步：Backlog 是你的第一个护栏（见第四节）

自动启动默认关闭；开启后只有 3/3 任务自动开跑。说明框是你写下团队规则的地方——什么算复杂、什么算可验证。

## 七、完成与成本

- **完成**：定义完成、更新连接系统；工厂保留最终记录（PR、笔记、分支、执行历史）
- **性能视图**：读取交付、周期时间和成本信号——token 支出与计算支出分开，显示每个已关闭任务的**中位成本**
- **账单里的关键数字**：失败工作的支出。**这个数字决定你的 Backlog 资格是否过于宽松**——失败烧的钱就是资格评分太松的量化证据
- **盲区**：图表只覆盖托管模型和托管机器；自带 key 或 CI 用量不在内，需自己保留供应商预算

定价（云）：商业计划 199 美元/月/组织（14 天免费试用），含 50 美元月共享额度，之后从预付积分扣。托管模型 token 按供应商费率 **+10%**；自带 key 免这 10%。无按座付费；符合条件的开源项目可申请免费；自托管 = 自己付基础设施和模型钱。**重试也花钱**——这是绑定环存在的另一个理由。

## 八、诚实的权衡

1. **它的效果和你的检查一样好**。测试弱的仓库 → Verify 信号弱 → 又回到信任模型意见。这个工具奖励已经投资 CI 的团队
2. **自托管不轻量**。runner 资源堆积很快，独立开发者从云开始是理智的
3. **成本需要关注**。重试烧钱，失败工作支出是 Backlog 资格的温度计
4. **故意狭窄**。为有界、可检查的工作设计；「让客服设计你的新账单系统」不是它，文档也这么说
5. **放弃灵活性**。手卷脚本极具灵活性；一个有线条和画布的工厂更有主见。**观点就是护栏，但这是真实的交易**

## 九、开工前清单（把积压交给代理之前）

- [ ] 仓库有测试或 CI，东西坏掉时会失败
- [ ] Backlog 自动化里写下了「安全委派」的标准
- [ ] 首批任务是：小 bug、文档、失败测试、依赖问题
- [ ] 确定性检查在任何代理审核前运行
- [ ] 代理审查用「问题 + diff + 评分标准」，返回结构化结论
- [ ] 修正运行只提供简短失败摘录，而非完整历史
- [ ] 有重试次数限制和人工升级路径
- [ ] 人类在合并前还是会审核
- [ ] 跑过一个小批量基线，知道每个完成任务的成本
- [ ] 在托管模型和自带 key 之间做了选择

## 十、五个问题的深度回答

**Q1：护栏为什么该前置而不是只放在 PR 审核？**
因为末端审核的错误成本 = 一次完整的失败运行。前置评分的错误成本 = 一次评分。两者相差一到两个数量级的 token 和时间。更深一层：前置护栏把「什么是安全委派」从**每次会话的临时决定**变成**写一次的制度**——团队知识的固化点。

**Q2：为什么确定性检查必须先于模型判断？**
这与十五条实践里的「证据制度」同源：确定性检查（build/test/typecheck/lint）是**可重复的廉价现实锚点**，模型判断是不可重复的昂贵近似。正确的消耗顺序是：先用便宜且确定的东西过滤掉 90% 的失败，把模型判断留给「无法简化为命令」的剩余部分。顺序反过来，模型就在为 CI 本可免费回答的问题烧 token。

**Q3：重试上限为什么是最常被跳过的护栏？**
因为人自己接线时代理时，天然倾向「再试一次」。但「再试一次」没有终止条件就是**有损循环**：不稳定测试（flaky test）会让代理永远烧 token 修一个不是它弄坏的东西。重试上限 + 升级路径 = 止损机制。与我之前沉淀的 GPT-6 Astra「持久性」问题互补：Astra 的问题是**过早停**（首次实现就回来问），工厂解决的是**过晚停**——两个方向的护栏都必须在流程里显式存在，不能依赖模型的自觉。

**Q4：为什么定向反馈（失败摘录）优于全量执行历史？**
上下文是资源，不是档案。全量历史里有 90% 与本次失败无关的信息，它们不仅费 token，还会**稀释模型对失败原因的注意力**。这与我之前沉淀的「渐进式披露」是同一条规律：给模型「该去哪看」的指引，而不是强迫它读当下无关的一切。修正运行的正确载荷 = 触发条件 + 相关输出 + 任务边界 + 下一个必须过的检查。

**Q5：工厂模式放弃了灵活性，值得吗？**
值得，前提是你承认「灵活性」在多数团队里只是「每次重新决定」的美化说法。手卷脚本的灵活性 = 每条规则都活在操作者的脑子里，人走了规则就没了；工厂的主见 = 规则物化成画布和环。真正的代价是：**不适合有界工作的任务会被工厂的形态排除掉**——所以它的边界声明（不是给开放式工作设计的）恰恰是它诚实的部分。选型判断：信任 CI + 积压大量小 issue → 试一周，用「每个完成任务的成本」说话。
