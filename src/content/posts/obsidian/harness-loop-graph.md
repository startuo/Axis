## 30 秒答案

三个词解决所有混淆：

| 层 | 核心问题 | 一句话 |
|---|---|---|
| **Harness Engineering** | 模型周围搭什么 | 构建模型之外的**运行环境** |
| **Loop Engineering** | 怎么反复工作+验证 | 设计**重复执行与反馈**的循环 |
| **Graph Engineering** | 流程拓扑长什么样 | 用**节点、分支、汇合、状态转换**把流程显式化 |

心智模型：**环境 → 反馈 → 流程**

```
┌──────────────────────────────────────────────────┐
│                  HARNESS（环境）                    │
│  ┌────────────────────────────────────────────┐  │
│  │              GRAPH（流程）                    │  │
│  │  ┌──────────────────────────────────────┐  │  │
│  │  │          LOOP（反馈）                  │  │  │
│  │  │  Agent → Act → Observe → Decide      │  │  │
│  │  │    ↑                         ↓        │  │  │
│  │  │    └─── Grader ←── Evidence ←──┘      │  │  │
│  │  └──────────────────────────────────────┘  │  │
│  │  Node → Branch → Parallel → Join → Exit    │  │
│  └────────────────────────────────────────────┘  │
│  Tools · State · Permissions · Observability     │
└──────────────────────────────────────────────────┘
```

> 三个概念都围绕同一个模型，都影响可靠性，都可以包含"循环"。但它们不是同义词。一旦 Agent 离开 Demo Notebook，开始触碰文件、API、客户或生产代码，这三者的区分就不再是学术问题。

## 为什么这些术语突然重要了

裸语言模型**不能**创建文件、维护项目状态、运行测试套件、查看浏览器、执行审批规则、重启失败任务。这些能力来自它所在的**环境**。

随着 Agentic 软件成熟，一个标准的工程栈终于开始成形：

1. **底座**：Agent Harness——实际运行模型的代码
2. **中层**：Loops——处理重复执行和质量检查
3. **上层**：Graphs——映射出贯穿全过程的结构化路径

> 术语尚未完全标准化。"Agent Harness"在 2025 年下半年开始获得特定含义，"Loop Engineering"是 2026 年从业者中兴起的新术语，"Graph Engineering"应被理解为实践领域而非学术领域。

## 第一层：Agent Harness Engineering

### 定义

> **Agent = Model + Harness**（LangChain 官方公式）

Harness 是模型之外的代码、配置和执行逻辑。包括：系统提示词、工具定义、记忆、文件系统、沙箱、模型路由、handoff、中间件 hooks、上下文压缩、权限、日志、验证接口。

OpenAI Agents SDK 从运行时角度描述了同样的核心：**Runner** 调用模型、执行工具调用、处理 handoff、携带状态，只在达到真正的终止条件时才停止。

### Harness 这个词的价值

它把注意力从"模型崇拜"上移开。两个团队用同一个基础模型，结果可以截然不同——一个给了模型干净的工具、稳定的工作空间、受限的权限、可观测的状态；另一个给了模糊的 prompt 和一个不可靠的 API wrapper。

**智能可能相似，工作条件不同。**

### 一个严肃 Harness 通常包含的五层

| 子系统 | 内容 |
|--------|------|
| **Context Injection** | 指令、检索事实、对话状态、Skills、任务策略 |
| **Action Surfaces** | APIs、浏览器、Shell、代码解释器、数据库、MCP 工具 |
| **Persistence** | 文件、检查点、会话、进度日志、git 历史、长期记忆 |
| **Execution Control** | 超时、重试、预算、模型路由、子 Agent 生成、审批门 |
| **Safety & Governance** | 权限、隔离、allowlist、密钥处理、人工授权 |
| **Observability** | traces、工具输入输出、状态转换、成本、延迟、评估结果 |

### Harness 工程发挥价值的地方

- **长时间任务**：Anthropic 发现单纯靠上下文压缩不够，需要初始化器 + 进度文件 + git 历史 + 增量工作纪律
- **跨会话连续性**：Agent 需要知道"发生了什么"和"还有什么要做"
- **可控性不足时**：Agent 没有某种能力、无法干净恢复、丢失状态、访问太多、不可审计、环境不一致

**判断标准**：把模型从架构图中拿掉。剩下的所有东西大概都是 Harness——工具、数据访问、状态存储、沙箱、中间件、评估器、重试策略、UI。

## 第二层：Loop Engineering

### 从 Agent Loop 到 Loop Engineering

每个使用工具的 Agent 都有一个内嵌的小循环：

```
call model → look at results → run tools → input observations → repeat
```

Loop Engineering 的开始，是**有意识地在那个行为之外构建或堆叠新的循环**。

### 三种核心 Loop 类型

| 类型 | 模式 | 例子 |
|------|------|------|
| **Verification Loop** | Agent 产出 → 确定性检查/Grader → 明确反馈 → 只在有证据时重试 | 测试通过？链接有效？Schema 校验通过？审查者批准？ |
| **Event-Driven Loop** | 调度/Webhook/新文档 → 唤醒 Agent | Cron 日报、CI 触发、文档变更响应 |
| **Improvement Loop** | 分析 traces & 失败 → 修改指令/工具 → 测试新版本是否更好 | 从生产日志中自动优化 prompt |

LangChain 2026 年的框架将这些称为**"循环的堆叠"，而不是一个魔法 while 语句**。

### 一个良好工程化 Loop 的 8 大组件

| 组件 | 回答的问题 |
|------|-----------|
| **Trigger** | 什么启动下一轮？用户请求？调度？测试失败？新数据？评估反馈？ |
| **Goal** | 要到达什么具体状态？不是模糊的"继续改进" |
| **State & Memory** | 下一轮需要知道什么，而不需要重放一切？ |
| **Action Policy** | Agent 可以改变什么？调用什么？委托什么？花多少？ |
| **Evidence** | 测试、Schema 校验、引用、diff、指标、人工审查 |
| **Feedback** | 为什么证据未达标的**紧凑、可执行**描述 |
| **Stopping Rule** | 成功？预算耗尽？超时？不可恢复错误？人工升级？ |

### Loop Engineering ≠ Prompt Engineering

| Prompt | Loop |
|--------|------|
| 告诉模型**调用期间**做什么 | 指定系统**调用之后**做什么 |
| 一次指令 | 观察结果 → 选择反馈 → 决定是否继续 → 持久化进度 → 终止 |

### 核心原则

> **不要靠置信度循环。靠证据循环。**
> "Agent 说它做完了"不是停止条件。"测试通过、链接有效、Schema 校验通过、审查者批准"才是。

### 成本权衡

每个 Grader、审查者、重试都增加一次模型调用或工具运行。Anthropic 的指导原则：**偏好最简单的可行架构，只在性能增益大于成本时才增加 agentic 复杂度。** Loop 也一样——在**失败成本 > 验证成本**的地方才加。

## 第三层：Graph Engineering

### 定义

Graph Engineering 问的是不同的问题：不只是 Agent 做什么，而是**什么组件被允许在接下来运行**。步骤是节点，允许的步骤是边。边可以表示**序列、条件分支、并行 fan-out、汇合、循环、人工中断**。

状态在图中穿行，拓扑保证所需控制流可被验证。

### 两大框架对比

| 维度 | LangGraph (LangChain) | GraphFlow (AutoGen) |
|------|----------------------|---------------------|
| **定位** | 低层编排基础设施，持久执行 + 状态 + Human-in-the-Loop | 有向图 Agent 执行，灵活编排多 Agent |
| **驱动方式** | 显式图定义 + 状态管理 | DiGraphBuilder API + 条件边 |
| **核心优势** | 确定性工作流、审计追踪、持久化、长期运行 | 顺序/并行/条件/循环四种模式原生支持 |
| **Token 效率** | 高（Agent 只看到需要看到的部分） | 较低（对话模式，完整历史） |
| **2026 状态** | LangGraph 1.0 生产就绪 | AutoGen 进入维护模式，建议迁移到 Microsoft Agent Framework |

### Graph 工程师的实际决策清单

| 决策 | 含义 |
|------|------|
| **节点边界** | 哪些工作属于确定性函数？LLM 调用？专家 Agent？人工审查步骤？ |
| **状态 Schema** | 每个节点可以读写什么？并行更新如何合并？ |
| **路由条件** | 什么证据让工作往前走、往回走、旁路走、升级？ |
| **并发** | 什么可以并行？什么必须汇合？什么共享资源需要协调？ |
| **循环与出口** | 哪里允许重试？允许多少次？什么让循环安全？ |
| **持久性** | 检查点在哪里？中断后如何恢复？ |

### 什么时候 Graph 值得这个仪式感

**适合**：流程有有意义的分支、并行工作、审批、恢复路径、多个专家 Agent 时。

**不适合**：任务就是"给一个 Agent 三个工具让它自己干"时。

> Graph 可以改善调试，但也可能过早冻结假设。如果模型必须动态发明计划，把每个可能路径强行塞进图里会让系统**更脆弱而非更健壮**。

## 三层如何在一个真实系统中协作

以"研究并发布一份行业简报"的 Agent 为例：

```
HARNESS 层
├── 文件系统（存草稿）· 浏览器工具（查资料）· 权限（只读外部 API）
├── 状态存储（进度归档）· 可观测性（每步 trace）· 人工审批（发布前）
│
└── GRAPH 层
    ├── 研究节点 → 审核节点 → 撰写节点 → 审查节点 → 发布节点
    │       ↑                                    │
    │       └──── 退回修改（条件边）←──────────────┘
    │
    └── LOOP 层（嵌入在 Graph 节点中）
        ├── 研究 Loop：搜索 → 读取 → 判断覆盖度 → 不够再搜
        ├── 撰写 Loop：起草 → 事实核查 → 修正 → 再核查
        └── 审查 Loop：评分 → 反馈 → 修改 → 重评
```

**嵌套关系**：Graph 在 Harness 内运行；一个或多个 Loop 在 Graph 内运行；Harness 提供这些 Loop 需要的状态、工具和评估器。

## 按故障诊断选择工程层

| 症状 | 从哪层入手 | 可能解决 |
|------|-----------|---------|
| Agent 无法安全访问正确数据或工具 | **Harness** | 工具契约、权限、沙箱、上下文注入 |
| Agent 跨会话遗忘进度 | **Harness** | 持久状态、检查点、进度 artifacts、压缩 |
| 第一次尝试接近但不稳定 | **Loop** | 外部 Grader、确定性测试、反馈+有限重试 |
| Agent 成功后继续工作 / 证明前就停 | **Loop** | 基于证据的终止状态 + 预算感知停止规则 |
| 多个专家必须按受控顺序运行 | **Graph** | 显式节点、边、路由条件、汇合 |
| 多步流程中难以定位失败 | **Graph + Harness** | 与图节点对齐的有状态 traces |
| 工作流变化太频繁不适合固定图 | **更简单的 Harness** | 保持模型驱动控制；推迟图的形式化 |

## 常见错误（反模式）

### 1. 理解工作之前就建图

团队有时在观察一个有能力的 Agent 实际如何解决之前，把业务流程翻译成几十个节点。**先从一个更简单的 Harness 收集 traces，再把稳定的路径形式化。**

### 2. 让同一个模型既写又评，没有安全网

自我审查有帮助，但容易出现共享盲点。**优先确定性检查、分离审查者上下文、对高影响操作要求人工批准。**

### 3. 用"继续试"作为 Loop 规格

无界重试循环是成本泄漏。**每个 Loop 需要可衡量目标、新鲜证据、最大尝试次数、命名升级路径。**

### 4. 把 Harness 当垃圾桶

更多工具和记忆不自动等于更好。**工具过多 → 选择错误；上下文嘈杂 → 混乱；权限过宽 → 风险。**

### 5. 把编排失败归咎于模型

模型无法可靠补偿：过期状态、模棱两可的工具 Schema、损坏的 API、缺失的退出条件。**改进出故障的那一层。**

## 生产就绪检查清单

### Harness
- [ ] 工具是否**窄**、有文档、可观测？
- [ ] 状态是否**持久**？
- [ ] 权限是否**最小化**（least-privilege）？
- [ ] 操作者能否**暂停、检查、恢复**一次运行？

### Loop
- [ ] 什么**证据**证明成功？
- [ ] 失败时返回什么**反馈**？
- [ ] 允许多少次**重试**？
- [ ] **预算耗尽**时会发生什么？

### Graph
- [ ] 哪些路径**必须是确定性**的？
- [ ] 哪里可以**并行**工作？
- [ ] 什么**状态**是共享的？
- [ ] 哪里有人工**门禁**和**恢复路径**？

### 评估
- [ ] 团队能否**重放**真实 traces、**对比**版本、将改进**归因**于具体变更？

### 运维
- [ ] 生产环境监控：成本、延迟、失败率、人工干预率、任务级成功率？

## 记忆口诀

> **Harness 搭环境，Loop 管反馈，Graph 画流程。**
>
> 没有一个能替代另外两个。
> - 画得再美的 Graph 也救不了丢失状态的 Harness
> - 再好的 Harness 没有证据和停止规则的 Loop 也是在烧钱
> - 精心设计的 Loop 当分支、并行和审批嵌在 ad-hoc 代码里时一样难以运维
>
> **三者联合设计，才能产生可靠的 Agent 系统。前提是团队清楚每一层解决什么问题。**

## 延伸思考

### 1. 三层与 Agent Skills 生态的关系

rvaniaaaa 的 8-Agent 自主技能发现流水线（[详见研究笔记](/posts/obsidian/continuous-learning/)）本质上是在解决 **Harness 层的供给侧问题**：如何让 Agent Skills 自动生成而不是人手工写。这会让 Harness 的 Fat Skills 部分越来越丰富，但也会加剧 Skill 质量审查的需求——这又回到 Loop 层的 Verification Loop 设计。

### 2. "薄 Harness、厚 Skills"的极限

Garry Tan 的原则是"Thin Harness, Fat Skills"。但当 Skills 数量从 26 个增长到 26,000 个（自主发现流水线的终局），Harness 的 Context Injection 层如何做 Skill 路由和选择？这需要 **Graph Engineering** 的思维——不是硬编码调用顺序，而是定义状态驱动的 Skill 选择拓扑。

### 3. 从"修复层"到"设计层"

文章给出的故障诊断矩阵是**反应式**的——先看到症状，再选择层。但成熟的 Agent 工程应该是**设计先行**的——在开始编码之前就决定：
- 这项任务的"环境"（Harness）需要哪些约束？
- 质量门禁（Loop）的证据标准是什么？
- 哪些步骤的拓扑（Graph）必须固定，哪些留给模型自主？

### 4. 评估困境

三层架构让系统更可靠，但也让评估更复杂。改进来自哪一层？如果换了工具（Harness 改动），测试通过率提升了，能说是"工具更好"还是"工具和 Loop 的新组合更好"？需要**分层 A/B 测试**——一次只变一层，记录归因。
